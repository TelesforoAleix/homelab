- **Phase:** 20.0 — a sub-phase of Phase 20 (Factory Rewrite)
- **Written:** 2026-09-11
- **Status:** Brief, committed before implementation per ADR-017
- **Implements:** ADR-035 §2, §4, §5, §7; ADR-034 §6 (the consuming half)
- **Repository of record for the code:** `factory` (public). The plan stays here (ADR-031 §9,
  ADR-035 §9).

## 0. Governance note

### 0.1 Why this is a sub-phase and not Phase 20

Phase 20 is the Factory rewrite: keep the content, discard the markdown-heavy format. That is a
conversion of roughly ten thousand lines of prose, and the Phase 19 design review split it, because
converting prose into a loadable operating model **before the harness that consumes it exists**
shapes the conversion around a guess.

What can be built now is the executable slice: a Workbench that manages one project's records, plus
the synthetic project that proves it end to end. That is useful on its own — it discharges ADR-031
§4's standalone-quickstart criterion, outstanding since the layers were named — and its only
prerequisites, ADR-034 and ADR-035, are accepted.

So this is `20.0` under the roadmap's sub-phase rule, and Phase 20 proper remains open and now runs
after Phase 23.

### 0.2 This phase writes code into a different repository

Every phase so far has changed `homelab`. This one's deliverable lands in `factory`. The plan,
the brief and the handover stay here (ADR-031 §9 as amended, restated by ADR-035 §9); the software
lands there. Both repositories are public, and the boundary gate applies to both.

### 0.3 The node is not touched

Nothing in this phase reaches the reference node. Workbench's first real deployment is the MacBook
(ADR-035 §7). ADR-032's content gate is not engaged, because the synthetic project is deliberately
public and synthetic. Phase 13 and Phase 14 are unaffected and can run in parallel.

## 1. Purpose

ADR-035 replaced ADR-031 §1's *"Factory never executes"* with a narrower boundary:

> **Factory Workbench executes Factory project operations; the configured backend executes AI and
> concrete tools.**

This phase builds the minimum of that, and the fixture that proves it.

The measure of success is not "Workbench exists". It is **ADR-031 §4, satisfied by demonstration**:
someone takes `factory` alone, with no homelab, and runs a project end to end.

**Verified 2026-09-11 by reading `/Users/home/Code/factory` at `97ccb86`.** The design review

**The read half substantially exists.** `dashboard/` already loads a project workspace or its `ops/`
folder and renders tasks, tickets, runs, reviews, approvals, the inbox and learning records, with

database and no build step.

**It is read-only by construction**, not by omission: `dashboard.js:101` calls
`showDirectoryPicker({ mode: "read" })`. Its own README states the boundary — *"It does not write
tickets, runs, approvals, or other operational state"* and *"Avoids server, database, CLI bridge, and
write actions in this slice."*

### 2.1 Factory already planned both halves, and already analysed the decision

**Amended 2026-09-11, on the owner's correction.** The first draft of this brief treated the existing
dashboard as a finished artifact to inherit and presented §6.1 as an open decision to make fresh.
Both were wrong, in opposite directions.

`roadmap.md` runs V1.5 → V1.6 → V2 → V3, and the later entries are **not** a vague intention:

| | Scope | State |
|---|---|---|
| **V1.5** | Read-only management dashboard | Built |
| **V1.6** | Drill-down: task→tickets, ticket→runs/reviews/release/context, filters, relationship index | Marked *"planned"*, but the dashboard README describes drill-down and filtering as working. **Verify rather than trust either label** |
| **V2** | CLI bridge, context-pack generation, run logging, git awareness | Not built |
| **V3** | Writable control plane: project overview, work hierarchy, board, roster/org chart, founder inbox, run ledger, approvals, release readiness, improvement queue | Not built |

**V3's scope list is this phase's functional target**, not something to re-derive. V2's CLI bridge
sits between, and its content is directly relevant.

**The bridge decision is already analysed in Factory.** V1.5's own exit criterion reads *"No write
actions are introduced before the CLI/server/webview bridge decision"* — Factory named this decision
before I did. `design/paperclip-style-management-interface.md` carries the analysis:

- §*"Requires CLI, Local Server, Or VS Code Webview Later"* lists exactly what cannot be done from a
  browser: creating and updating records, assignment, answering inbox items, approvals, review and
  release records, file watching, running validation, and git staging/commit/push.
- Its **Safety Rules** are already written and should be adopted rather than reinvented: *no
  automatic commits*, ***no broad filesystem write path***, *show the source file for every rendered
  object*, and *any future write path must validate the object and leave an audit trail*.
- Its Phase 4 (`DASH-301`–`304`) and Phase 5 (`DASH-401`–`405`) decompose the work, and `DASH-405`
  already calls for *"audit trail and rollback/previous-hash metadata for mutations"*.
- `design/open-questions.md` §*"Dashboard Bridge"* poses four questions, the first of which is
  **"Should the first bridge be CLI-first?"**

**ADR-031 §9 superseded the V-series as a *plan*. It did not kill the design content**, which
ADR-031 §7 explicitly keeps. Reading these documents as input is correct; treating `roadmap.md`'s
sequencing as binding is not. Retiring the V-series remains Phase 20's work.

### 2.2 What exists is an MVP, not a constraint

Stated plainly because the first draft implied otherwise: **nothing in `factory/` is a finished
state.** It was built as a way of *seeing* the system and it stopped at read-only. Where it works, reuse
it and skip the rebuild. Where it does not, rethinking it is in scope — including the data shapes,
the rendering, and the dashboard's structure. **"It is currently like this" is not a reason to keep
it.** The only genuinely fixed constraints are the ones in §5, which come from accepted ADRs.

## 3. Learning objectives

By the end the owner should be able to explain:

- why Workbench holding no credential, no model registry and no tool implementation is the line that
  keeps ADR-031 §1's reason intact, even though Factory now executes;
- why a browser page alone cannot run the acceptance project, and what that forces (§6.1);
- what a deterministic fake adapter buys, and why it ships before any real one;
- the difference between a task closing and a change being published, and why a human approval bound
  to an exact revision is not the same as an approval of a pull request;
- how to run the synthetic project from a clean clone, and what each planted refusal proves.

## 4. Functional objectives

1. **Open** an existing project by being pointed at its root or its `ops/`.
2. **Create** a new project and its minimum valid `ops/` structure from `templates/ops/`.
3. **Read and render** tasks, tickets, inbox, team, reviews, approvals and workflow state.
4. **Validate and write** those records — the half that does not exist today.
5. **Invoke AI work** through one configured adapter, with the **deterministic fake** implemented
   first.
6. **Refuse**, correctly and legibly, in the six planted cases in §8.2 plus the two structural ones.
7. **Run the synthetic acceptance project end to end with no homelab installed.**

**The write half is the point of this phase.** Everything Factory has today is read-only; what it
needs is to become *interactive*. V3's scope list is the functional target and is reproduced here so
it is not re-derived: project overview, work hierarchy browser, task/ticket board, agent roster and
org chart, founder inbox, run/session ledger, approvals, release readiness, and improvement queue.

Not all of it need land in 20.0 — this is the *minimal* Workbench, and the brief's own test is
objective 7, not feature parity with V3. What must land is enough of the write path that the
acceptance project runs, plus whichever read surfaces that exercises. Anything beyond that is Phase
20 or later, and should be named in the handover rather than half-built.

### 4.1 The fourteen acceptance steps

Accepted in the design review and enumerated here, because a brief that points elsewhere for its
primary acceptance artifact is not implementable on its own.

| # | Step | Note |
|---|---|---|
| 1 | Create a project proposal | |
| 2 | **Require human approval before creating its repository** | Gate |
| 3 | Initialise the repository and minimum `ops/` structure | |
| 4 | Create a feature branch or disposable worktree | Needs process execution (§6.1) |
| 5 | Create a task with metadata and acceptance criteria | |
| 6 | Assign work through an orchestrator to approved implementation and review agents | |
| 7 | Select and assemble bounded context | |
| 8 | Execute through one adapter | Deterministic fake |
| 9 | Permit automatic edits, commits, tests, review and revision **on the feature branch** | Needs process execution |
| 10 | Push the feature branch | Needs process execution |
| 11 | **Refuse direct agent writes to `main`** | Refusal 7 in §8.2 |
| 12 | Create a pull request in GitHub mode | Needs `gh` |
| 13 | **Require a human approval bound to the exact reviewed revision before merge** | Refusal 8 in §8.2 |
| 14 | Merge and record provenance | |

**The synthetic project is one artifact doing five jobs**: the standalone quickstart, the end-to-end
acceptance test, the development fixture, the learning example, and the planted-control environment
for refusals.

**Two modes.** The default uses a **disposable local bare Git remote** — repeatable, credential-free,
safe for tests. Steps 12 and 13's pull-request form is exercised in **GitHub mode**, which is opt-in
and uses the already-authenticated `gh` CLI. A local-mode run must still prove steps 11 and 13's
refusals; those are properties of Workbench, not features of GitHub.

**Steps 4, 9, 10 and 12 are the ones a browser page cannot perform**, which is what makes §6.1 the
phase's first decision rather than a detail.

## 5. Decisions already fixed

Inherited and **not** reopened by this phase:

- **ADR-035 §2** — Workbench holds no homelab credential, no model registry, no tool implementation.
  This is the phase's hard constraint.
- **ADR-035 §4** — adapters; only the deterministic fake is fixed, and it comes first.
- **ADR-035 §7** — credentials use the OS credential store where available, otherwise environment
  variables or a protected user-local file **outside every repository**. Never in project `ops/`,
  committed configuration, logs or browser storage. GitHub mode uses the already-authenticated `gh`
  CLI; Workbench stores no GitHub token. Local Workbench binds `127.0.0.1`, no application login.
  Public exposure is out of scope.
- **ADR-034 §6** — compatibility is checked **before activation**, naming every missing requirement.
  "Load now, discover refusal at dispatch" is rejected.
- **ADR-034 §12** — humans add agents to a project; the orchestrator may recommend through the inbox
  but may not approve or edit the roster.
- **ADR-031 §11** — agent manifests are JSON. Not reopened.
- **ADR-013** — `main` stays known-working; feature branches for unfinished work.
- Repository visibility defaults to **private** in GitHub mode; making one public is a separate
  explicit approval. Agents never push to `main`; all GitHub changes go through a pull request.

## 6. Decisions still open

### 6.1 The one that shapes everything: browser-only, or a local process?

**This is the phase's central design decision and it should be made first.**

**This is Factory's own CLI/server/webview bridge decision** (§2.1), not a new one. This phase
resolves it; it does not pose it.

Two facts bound the answer, and neither is a preference:

- **A browser page cannot spawn `git`, `gh`, or a test runner.** Acceptance steps 4, 9, 10 and 12
  need exactly that, and Factory's own analysis already lists these as out of browser reach.
- **Browser writes need `showDirectoryPicker({ mode: "readwrite" })`, which is Chromium-only.**
  Firefox and Safari do not implement it, so a browser-write Workbench cannot save for some adopters.

ADR-035 §7's *"binds to `127.0.0.1`"* presumes a server. It is **one line in an ADR about scope, not
an architecture decision**, and this phase may conclude otherwise provided it says so.

| Option | What it costs | What it keeps |
|---|---|---|
| **CLI-first bridge** — dashboard stays a `file://` page for viewing; a `factory` CLI does every validated write | Two surfaces to learn; the UI cannot write directly | **The file-based dashboard exactly as it is.** Matches Factory's own `DASH-301`–`304` and its first open question |
| **Local server** — one process serving the UI and doing writes | A process to run; a language and runtime choice | One surface; satisfies ADR-035 §7 literally |
| **Hybrid** — CLI first, a thin server added later once write semantics are proved | Sequencing discipline | Both, in order, with the risky half deferred |
| **Browser-only** | Cannot run git, tests or `gh`. Chromium-only. **Fails objective 7** | — |
| **CLI only, no UI** | Discards a working dashboard and the "Workbench is the main interface" premise | Lowest cost |

**The first draft of this brief called a local server "the expected outcome". That was premature** —
it underweighted the CLI-first option, which keeps the dashboard as a file exactly as it is today,
gets validated writes, satisfies every acceptance step, and is the option Factory's own design
documents reach for first. It is recorded as a correction rather than edited away.

**Adopt Factory's existing safety rules for whichever path wins**: no automatic commits, no broad
filesystem write path, show the source file for every rendered object, and every write validated
with an audit trail carrying actor, timestamp and git visibility (`DASH-405`).

**Language and runtime are open.** Python matches homelab's existing services and the owner's
demonstrated ground; Node matches the existing dashboard code. Whichever is chosen must keep
dependencies minimal per `AGENTS.md`.

### 6.2 Record serialisation for project `ops/`

ADR-031 §11 fixed **agent manifests** as JSON. It said nothing about project records, and the
existing templates are YAML with one JSON (`run.json`) and two Markdown. Whether Workbench writes
what the templates already use, or normalises, is this phase's call — **if it changes anything, that
is cross-phase and needs an ADR** (ADR-017), because `dashboard.js` and every existing template
depend on it.

### 6.3 Where the synthetic project lives

Inside `factory` as a subdirectory, or generated into a temp directory on demand. "Resettable"
argues for generated; "quickstart an adopter can read" argues for committed. Possibly both.

### 6.4 How much of §4's adapter list to implement

Only the deterministic fake is fixed. Whether a real adapter ships in this phase at all is open, and
**not shipping one is an acceptable outcome** — objective 7 is satisfied by the fake.

## 7. Implementation scope

Expected work, not exact commands before discovery:

1. **Read Factory's existing design documents** — `design/paperclip-style-management-interface.md`,
   `design/v0-operating-objects.md`, `design/open-questions.md`, and `roadmap.md` V1.6/V2/V3. They
   contain prior analysis of most of this phase's questions (§2.1).
2. **Decide §6.1**, and record it. Everything else depends on it.
3. **A record layer** — read, validate and write the `templates/ops/` object types, with validation
   refusing an invalid record rather than writing it.
4. **Project lifecycle** — open an existing project; create a new one with minimum valid `ops/`.
5. **The adapter interface**, plus the **deterministic fake**. The interface must be shaped so that
   "run this through homelab" and "run this through Claude Code" are the same shape (ADR-035 §4) —
   that is the property this phase must not get wrong, because every later adapter inherits it.
6. **Compatibility check before activation** (ADR-034 §6), naming every missing requirement.
7. **Approval and budget gates** — an approval bound to one immutable proposed action including its
   target and revision; two budget limits, monetary and model-call, with the first reached stopping
   execution and raising an inbox request.
8. **The synthetic acceptance project** — §4.1's fourteen steps and §8.2's planted refusals.
9. **The UI.** Start from `dashboard/` and **reuse what works** — it already renders every record
   type this phase touches. Rework or discard what does not: it is an MVP built to see the system,
   not a specification. Reuse is the default because it is cheaper, not because the code is fixed
   (§2.2).
10. **A standalone quickstart** in Factory's README — ADR-031 §4's actual deliverable.

**Explicitly out of scope:** migrating Factory's catalogue or content (Phase 20); any homelab
integration or adapter (Phase 23); the homelab administration dashboard (Phase 22); concrete homelab
tools (Phase 19); retiring Factory's V-series roadmap entries (Phase 20); anything touching the node.

**Not out of scope: rethinking what exists.** Reworking the record shapes, the rendering or the
dashboard's structure is permitted where the MVP does not hold up (§2.2). What is out of scope is the
*wholesale* content conversion, which is Phase 20. If a rework turns out to be cross-phase — record
serialisation is the likely case (§6.2) — it becomes an ADR rather than a silent change (ADR-017).

## 8. Validation / tests

**An authorisation check that has only ever permitted is unvalidated.** Every refusal below is proved
by attempt against a **planted positive control** — the byte-identical case with only the offending
element removed, which must succeed. A refusal with no passing control proves only that the code is
broken.

### 8.1 The end-to-end proof

1. From a **clean clone of `factory` alone, with no homelab installed**, the synthetic project runs
   all fourteen steps of §4.1 on the deterministic fake adapter.
2. The run is **repeatable**: reset and re-run produces the same result.
3. ADR-035's second-adapter check — the same project runs on a second adapter **without its records
   changing**. This is what distinguishes a real abstraction from one implementation with an
   interface drawn around it. If only the fake exists, this is deferred to the handover **and named
   as unproved**, not quietly skipped.

### 8.2 Planted refusals, each with its positive control

| # | Refusal | Control that must pass |
|---|---|---|
| 1 | An unapproved agent addition to the roster | The same addition, approved |
| 2 | An agent requiring a capability the backend does not advertise | The same agent, requirement met |
| 3 | An approval-gated action with nothing in the inbox | The same action, approved |
| 4 | Review rounds exhausted (default 2, per-project configurable) | The same loop resolving in one round |
| 5 | Budget exhausted — **both** the monetary and the model-call limit, separately | The same task within budget |
| 6 | An agent exceeding project or context scope | The same agent inside scope |
| 7 | **A direct agent write to `main`** | The same write to a feature branch |
| 8 | **A merge whose human approval is not bound to the exact reviewed revision** | Approval bound to the reviewed revision |

Refusal 2 must name **every** missing requirement, not the first — that is ADR-034 §6's specific
claim and a test that lists one is not testing it.

Refusal 8 must be proved by **changing the revision after approval** and confirming the approval no
longer holds. An approval that was never invalidated has not been shown to bind.

### 8.3 Secrets and exposure

- A grep of the Workbench tree and of a fixture project's `ops/` finds **no credential**, and a
  completed run produces none in its logs.
- If §6.1 lands on a local process: it listens on `127.0.0.1` only, checked with `ss`/`lsof`, not
  assumed from configuration.
- The ADR-029 §5 boundary gate passes in `factory` before anything is pushed.

## 9. Security considerations

**The credential boundary is the thing most likely to be broken quietly.** Workbench is the first
Factory artifact that touches credentials at all. ADR-035 §7's rule is absolute: never in project
`ops/`, committed configuration, logs, or browser storage.

**`gh` is an ambient authority.** GitHub mode uses the user's already-authenticated CLI, which means
Workbench inherits whatever that account can do — including repositories unrelated to the project.
Repository creation requires human approval, visibility defaults to private, and making a repository
public is a separate explicit approval.

**The default local remote is a disposable bare repository**: repeatable, credential-free, safe for
tests. GitHub mode is opt-in.

**No node access, no privileged operation, no destructive host command.** If a real adapter is
implemented, ADR-025's locks apply unchanged — ADR-034 §13's change takes effect in Phase 23, not
here.

The synthetic project is **deliberately public and synthetic**. It must contain nothing real: no
owner data, no private path, no token-shaped string, not even a plausible one.

The handover must state, explicitly:
