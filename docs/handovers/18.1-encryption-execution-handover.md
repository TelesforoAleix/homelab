# Phase 18.1 Handover — Encryption execution

- **Phase:** 18.1 — a sub-phase of Phase 18 (Foundations)
- **Brief:** [`18.1-encryption-execution.md`](18.1-encryption-execution.md), committed before
  implementation per ADR-017
- **Executed:** 2026-09-12, at the console and over SSH, per the runbook's stage order (A–E)
- **Addressed to:** Phase 18.2 (migration), Phase 12 (scheduling/monitoring/notifications), Phase 13
  (hardening), Phase 14 (recovery)

## Outcome

**Complete.** ADR-037 is true on the machine, not only on paper. Root is smaller; a 128 GiB LUKS2
volume exists in the freed space; it opens with the passphrase and refuses without it; the node
survived a real power cut unattended, came back locked, and told the owner so when asked; a
volume-dependent service, started while locked, was skipped rather than failed; and nothing about the
bot or the node's exposure regressed. ADR-046 — the decision ADR-037 §6 deferred, on what happens to
the credentials that stay on root — is **Accepted**.

**§6.5 (a lock-state line in the bot's `/status`) was declined by the owner, not deferred.** See
below — it is not something Phase 12 inherits as unfinished work.

## What the next phase inherits

### Phase 18.2 — by name

1. **The volume as built:** `ubuntu-vg/data`, 128 GiB, LUKS2, mapper `homelab-data`, ext4 label
   `homelab-data`, mounted at `/srv/homelab`, root-owned and empty except the probe's file. Ownership
   and layout inside it are undecided — 18.2 decides who owns what.
2. **The reserve: 11,116 free extents = 43.42 GiB**, deliberately unallocated. Growing either volume
   is online and needs no console: `lvextend -L +NG ubuntu-vg/data && cryptsetup resize homelab-data
   && resize2fs /dev/mapper/homelab-data`; growing root is `lvextend -r -L +NG ubuntu-vg/ubuntu-lv`.
   Never allocate the last extent — the reserve is also the snapshot space this project has never had.
3. **The service pattern, proved twice** (start-while-locked, D3's real power cut):
   `ConditionPathIsMountPoint=/srv/homelab`, `PartOf=homelab-data.target`,
   `WantedBy=homelab-data.target`, `After=`. `Condition`, not `Assert` — a skipped unit stays
   `inactive` with the reason in the journal; `systemctl --failed` and `is-system-running` are
   unaffected. **`systemctl start` of a skipped unit returns 0** — scripts must check `is-active`,
   never `start`'s exit code. The probe (`homelab-data-probe.service`) is the reference
   implementation; 18.2's first real service replaces it as the canary and removes it, saying so.
4. **Workbench must refuse to start while locked** (ADR-038's third validation) — this pattern is how,
   and 18.2 proves it with Workbench itself, refusal and control, the same way C13 proved it with the
   probe.
5. **Docker's data root is on unencrypted root.** Anything holding knowledge or project content
   bind-mounts from `/srv/homelab`, or `data-root` moves into the volume and Docker gains the
   Condition — which makes Docker wait on unlock. Decide, and record it as an ADR if `data-root`
   moves.
6. **The mountpoint is immutable underneath** (`chattr +i /srv/homelab`). Anything that wants to write
   must be on the mounted volume. Do not `chattr -i` it to make something work — C8's fallback exists
   for a reason that should not recur.
7. **Backup scope changes but has not been decided.** `backup-node.sh` now covers the volume's boot-
   class *configuration* (§10 below) but deliberately not its *contents*. Repositories have remotes;
   `brain`'s remote is its backup. 18.2 says whether that is enough or whether the volume needs its
   own backup path.
8. **The header backup must be re-taken if 18.2 changes a keyslot.** It exists as of the closeout
   review, not as of the original execution window — see §Problems. Confirm it is actually on the
   card before treating it as a settled fact rather than a claim.
9. **A cross-cutting standard was recommended, not written.** The brief's §13 suggested
   `docs/standards/volume-dependent-services.md` for the three directives above, since Phase 12, 18.2
   and 23 all consume the pattern (ADR-043). It was not written in this closeout — it is documentation
   about a pattern, not a correction of drift, and was judged out of this stage's scope. 18.2 should
   write it before a second service copies the pattern by imitation rather than by contract.
10. **Any runbook that boots rescue media must say outright what the media is being used for in this
    instance**, not just what it's capable of — §Problems defect 7. 18.2 does not itself boot rescue
    media, but it should carry this rule forward to whichever of its own steps, if any, ends up
    needing a rescue boot.

## Validation performed

Every command below was run and its output checked by the orchestrator over SSH during execution;
this stage did not touch the node and reports the recorded results.

**The refusal proved before the volume held anything, and the pattern proved twice.** C13's planted
refusal — `systemctl start homelab-data-probe.service` while locked — returned **exit 0** with the
unit `inactive (dead)`, the journal reading verbatim: *"homelab-data-probe.service - Probe: data
volume dependency (Phase 18.1 fixture) skipped, unmet condition check
ConditionPathIsMountPoint=/srv/homelab."* Its positive control, after unlock, was both units `active`
with `.probe` holding a fresh timestamp. Nothing was written to root while locked (`test -e
/srv/homelab/.probe` → absent), and `systemctl is-system-running` stayed `running` with zero failed
units throughout — **locked is not degraded**, which is the phase's central claim and it is proved
both ways, not asserted.

**The power-cut test (ADR-037 validation 6) passed.** Mains pulled, 60 s, reconnected, nothing
touched: the node returned unattended and was reachable over Tailscale; boot was **27.625 s**
(firmware 13.120 + loader 3.831 + kernel 0.834 + initrd 3.349 + userspace 6.489) against the brief's
prediction of ~27.9 s — favourable; `is-system-running` → `running`, `--failed` → none; the boot
journal has **zero** mentions of `homelab-data`, `srv-homelab` or `ubuntu-vg-data`; the volume came
back **locked**, target and probe `inactive`; and **the Telegram bot answered `/status` from the
owner's phone while the volume was locked** — the recovery story ADR-046 §2 depends on, working.

**Boot safety, checked structurally, not just observed once.** `systemctl list-dependencies` against
`cryptsetup.target`, `local-fs.target` and `multi-user.target` all return **0** for anything
`homelab-data`-named — nothing pulls the volume in at boot. The generated unit
`systemd-cryptsetup@homelab\x2ddata.service` **exists**, so that zero is `noauto` doing its job, not a
broken entry (defect 4 below is why this distinction was checked explicitly). `findmnt --verify` → 0
errors (the `/swap.img` warning is normal and expected for a swapfile).

**Nothing regressed (ADR-037 validation 7).** `systemd-analyze security homelab-telegram-bot` → `1.3
OK`, unchanged. `id homelab-bot` byte-identical to Phase 07. `ss -tln` → 6 listeners, unchanged. The
Phase 18 console session (29) was closed deliberately at step B1, before the reboot, per the brief's
§6.1 decision — `loginctl` shows no `tty1` session at close, and the monitor and keyboard were
detached after the power-cut test (E1).

**C4 and C6 were run during this closeout, not at their scheduled step — a deviation worth recording
honestly rather than absorbing.** This documentation stage's first pass flagged both as unconfirmed
(§Open issues, below). The orchestrator's follow-up confirms **C6, the LUKS header backup, had never
been taken during execution** — the volume ran from B10 through the power-cut test with no header
backup existing anywhere, which is exactly the state ADR-037 §6 and ADR-046 §3 treat as a real gap:
had the header been damaged in that window, the volume would have been unrecoverable *even with the
correct passphrase*, and nobody had noticed. It was taken as a remediation once the review asked,
not during the original runbook. C4 (the wrong-passphrase refusal and its correct-passphrase control)
was likewise re-run at closeout rather than confirmed from the original execution. Their specific
command output was not relayed to this documentation stage in either case, so the DoD tables below
record them as **remediated late**, not as passed on schedule.

**Not confirmed at all, including after the follow-up:** the second keyslot and its two positive
controls (C5), and the same-day restore-before-reboot gate (A2). Still open — see **Open questions
for the orchestrator** in the stage report.

## Security notes

- **No key material for the volume exists on root.** Only `cryptsetup`'s interactive prompt was ever
  used; no keyfile, no TPM enrolment, no cached passphrase. This is the constraint ADR-046 §3 makes
  binding, and it is what makes §1's accepted risk small.
- **The five credentials on root are unchanged and are all revocable in minutes from the laptop**
  (ADR-046's table and loss procedure). This phase did not move any of them, by decision.
- **The mountpoint is immutable underneath** (`chattr +i /srv/homelab`) — a guard against root itself
  writing content there by accident, not a boundary against a deliberate write elsewhere on root.
- **This repository is public.** LUKS UUIDs and `lsblk`-shaped output may be recorded; passphrases,
  the header, and anything from the password manager may not, and none appear in this closeout.

## Problems / failures / lessons

**The brief's own runbook had seven defects, all findable by re-reading rather than re-executing, and
all the same authoring habit: written to be read once, not typed under pressure.**

1. **C11's install command contained an ellipsis** (`sudo install -m 644 … /etc/systemd/system/`)
   where real paths belonged — not executable as written. The brief also had not yet said that the two
   unit files do not exist anywhere before this phase writes them. Fixed mid-execution (`85c0eab` /
   `a9b98e7`), naming the write-then-`scp`-then-`install` path every config file has followed since
   Phase 03.
2. **C11's heredoc broke on an indented paste.** `EOF` must sit at column 0; the owner's terminal
   indented the pasted block, so the shell never saw the terminator.
3. **C9's `echo … | sudo tee -a` is not idempotent.** It ran twice and duplicated both the
   `/etc/fstab` and `/etc/crypttab` entries. Neither duplication produced an error. `findmnt --verify`
   caught the `fstab` one; the `crypttab` one was found only by reading the file by eye. The fix is
   check-then-append: `grep -q … || echo … | sudo tee -a`.
4. **C9's positive control named the generated unit unescaped.** systemd escapes `-` as `\x2d` in
   instance names, so `systemctl cat systemd-cryptsetup@homelab-data.service` can never find
   `systemd-cryptsetup@homelab\x2ddata.service` — a **false negative** that briefly looked like the
   unit did not exist at all. The correct form computes the escape:
   `systemctl cat "$(systemd-escape --template=systemd-cryptsetup@.service homelab-data)"`.
5. **D3's journal grep was too broad.** `ask-password` also matches systemd's own password
   infrastructure (`systemd-ask-password-console.path`, `-wall.path`, the socket), which starts on
   every boot regardless of whether anything is actually asking. It looked like a passphrase prompt
   and was not. The fix is to grep for the volume's own names, not the mechanism's.
6. **The runbook assumed multi-line paste works.** On the owner's terminal it does not: long lines
   wrap, and the wrap itself is entered as if typed. Four steps failed this way.
7. **B3 never says the sentence the step depends on.** §7.2 and step B3 send the operator into the
   Ubuntu installer ISO "for its shell only," and B3's own text warns not to reach the installer's
   *Install* flow — but nowhere does the brief say, in as many words, *"you are not installing
   anything; you are borrowing this environment's shell."* An operator who has just booted an
   installer and is told to find a shell inside it can reasonably wonder whether continuing into the
   installer is expected. Found only when a follow-up review asked why the rescue-boot step had
   caused confusion during execution. The fix is one added sentence, not a restructuring — but it
   has to be said, not implied by the surrounding cautions.

**Recommendation for Phase 18.2 and Phase 12:** one command per line, no heredocs, every append made
idempotent, every positive control run once — successfully — before it is written into a runbook as
fact. **Add for Phase 18.2 and Phase 14 specifically:** any runbook that boots rescue media must say
outright what the media is being used *for* in this instance versus what it is capable of doing —
Phase 14's bare-metal restore uses the identical ISO for a genuinely different purpose (a real
install, not a borrowed shell), and a runbook that doesn't distinguish the two in words invites the
same confusion with a much higher cost.

**A step was silently skipped during execution, and the review is what caught it.** C6 — the LUKS
header backup — was never taken during the original run. The volume existed, was opened and used
through the power-cut test, with **no header backup anywhere** for that entire window. Had the header
been damaged in that time, the volume would have been unrecoverable *even with the correct
passphrase* — precisely the failure mode C6 exists to prevent (ADR-037 §6, ADR-046 §3). Nobody noticed
until this documentation stage asked, in its first pass, "was C6 completed?", because the brief's own
material didn't confirm it either way. It was taken as a remediation once asked, not on schedule. The
lesson is procedural, not technical: a step whose absence has no visible symptom needs a positive
check in the runbook itself — "does a header backup exist off the node, yes/no" — not just an
instruction to perform it, because an operator moving through a long runbook can complete every step
that produces visible output and still skip the one that doesn't.

**B5 and B7's `e2fsck -f` exit codes were captured nowhere and are now unrecoverable.** The brief
requires both recorded (§15); the post-power-cut `dumpe2fs -h` shows the filesystem `clean` today,
which is evidence the filesystem is healthy *now*, but it is not evidence of what B5 and B7 actually
returned during the shrink itself, and that evidence cannot be reconstructed after the fact. The
lesson: the exit code of a destructive step has to be written down in the moment it runs, not
reconstructed from a downstream, unrelated check.

**§6.5 declined, not deferred.** The brief recommended a lock-state line in the bot's `/status`, and
the orchestrator's brief kept it in scope (reversing an earlier lean toward deferring it to Phase 12).
**The owner declined it on 2026-09-12**, because the bot's interaction model is due to be redesigned
and `/status` is adequate for what it does now. This is a decision, recorded with its reason — not
something Phase 12 inherits as unfinished. The observed consequence is honest, not softened: during
D3 the node sat locked and answered `/status` without mentioning it, which is exactly the gap a
lock-state line would have closed, and which Phase 12's push notification will close differently
(item 2 above).

**C1's `blkdiscard` proposal was declined for a reason worth keeping.** An earlier draft proposed
clearing the plaintext residue `resize2fs` leaves in the freed extents via a scratch LV and
`blkdiscard`, before creating the data volume. It was careful — it never named `ubuntu-lv` — and it
was declined anyway, not for danger but for **incoherence with ADR-046**: that residue is root's own
data, root stays unencrypted by accepted decision, and the same bytes stay readable on the live root
either way. Erasing the copy while leaving the original is ceremony. If the reserve is ever allocated
to something that does need a clean start, discard it then, with a reason, in that phase.

**Two committed config files did not match what §3a of this closeout's instructions specify as
installed.** `config/systemd/homelab-data.target` was correct; `config/systemd/homelab-data-probe.service`
held a duplicate of the target's contents rather than the probe unit. Both are corrected in this
branch to the exact text given as installed, matching the verbatim journal line quoted in
§Validation above.
