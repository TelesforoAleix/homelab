## 1. Purpose

Today the node has two things that answer a request: the Telegram bot, which is a *command* router
(`Router.dispatch(user_id, text)`), and the model helper, which is a *socket* that one account may
call. There is no place where "a request arrives from a client" is a general event. The Workbench
has an adapter interface with one implementation — a deterministic fake — and no code path that
calls it.

This phase builds **the endpoint**: one always-running, loopback-only service on the node that
accepts a normalised request from any local client, attaches the runtime's own record of where it
came from, classifies it cheaply, hands it to the model helper through the 15.0 wire protocol, and
returns the result to the client while recording what happened. It ships the **second adapter** —
`Workbench → homelab` — which is the thing that finally tests whether Phase 20.0's adapter
interface is real or drawn around one implementation.

It is deliberately the *thin* sub-phase. Layers 3–4 (does the request split, who handles each
piece), 6 (what the model sees), 7 (which model — already Phase 15's) and the governance machinery
(23.3) are not built here. A request that would need decomposition is classified as such and
**refused with that reason**, not partially served. The point is to have the pipe before the pipe
carries anything clever.

**Out of scope, by decision:** any metered call (ADR-033 §5 — the governor does not exist; the
endpoint reaches the two subscription providers through the helper and nothing else); task
decomposition; context assembly beyond forwarding what the client selected; the ADR-034 §13
transition (a model's output is still never dispatched — the Phase 09 canary applies, re-run here
unchanged); a scheduler client (23.1 or later); voice (17); re-routing the Telegram bot's `/ask`
through the endpoint (§6.7 — recommended deferred, with the reason).

**The Workbench (20.0, 18.2).** `factory/workbench/`, `python3 -m workbench.cli … serve` on

adapter. `Budget` implements the two limits with unknown cost kept unknown. Eight Factory roles exist

**Accounts.** `aleix` (admin; Workbench and helper run as it — ADR-047's two exceptions),
`homelab-bot` (bot, watchdog, notifier). No harness account exists.

**Egress (ADR-039).** The owner's own material may leave to approved providers when selected
deliberately by the owner or an approved agent on a work item; provenance travels with anything
assembled; providers are a configured list. Today the only egress is the helper's `question` +
`context` to the two subscription CLIs.

**Governance.** `safe-changes-headless.md` for anything boot-class (the endpoint's unit is);
`volume-dependent-services.md` if the unit touches the volume (§6.3 says it should not);
runbook rule from Phase 13 (print before wait; no piped sudo).

## 3. Learning objectives

- What an *entry* layer is and is not: why identity is attached by the runtime and never read from
  the request, and what breaks when a command router is mistaken for an endpoint.
- Why the endpoint holds no downstream credential and reaches the model only through a socket
  another account owns — and what that costs in unit-file terms.
- A request taxonomy small enough to be deterministic and honest enough to say "unclassifiable".
- How to prove an interface with a second implementation, and what "records do not change" means
  as a test.
- Why "always running" is a property of the system, and how the endpoint reports for duty when the
  volume is locked.

## 4. Functional objectives

1. **An always-running endpoint** on the node, loopback only, its own account, its own unit meeting
   the baseline, listed as the eighth socket. Up with the volume locked (§6.3).
2. **Entry (layer 1):** accepts a normalised request over HTTP on loopback from a local client;
   attaches origin (client name, peer credentials where the transport gives them, timestamp,
   request id) that the request body cannot set; refuses anything that tries.
3. **Understanding (layer 2):** a deterministic classifier with a closed taxonomy (§6.4); every
   request gets exactly one class or `unclassifiable`; classes that need layers 3–6 are refused with
   that reason at no cost.
4. **Forwarding:** a `question`-class request goes to the model helper over the 15.0 wire protocol
   with the client's `role` as routing key and the hints carried, unchanged; the helper's refusals
   come back distinguishable.
5. **Result handling (layer 9):** the result returns to the calling client with the request id;
   an audit line is written per request (ids, client, class, role, provider/model, outcome, cost or
   `unknown`, duration) — **never** the question, context or output (§6.5).
6. **The second adapter:** `workbench/adapters/homelab.py` in the `factory` repository implementing
   `Adapter` over the endpoint, selectable by configuration, plus the **smallest** Workbench action
   that calls the configured adapter — and the Phase 20.0 §8.1.3 check run for real: the same
   project on the fake and on `homelab` with its records byte-identical apart from the fields the
   adapter is allowed to fill.
7. **Nothing regresses:** `/ask` from Telegram unchanged; the helper's 15.0 fixture still 19/19;
   the Phase 09 canary re-run; Workbench tests pass on both adapters.

## 5. Decisions already fixed

- **ADR-038 §2** — loopback only, every client local, the MacBook reaches it through `ssh -L`.
- **ADR-047 / baseline** — the endpoint runs as **its own account**, never `aleix`, never
  `homelab-bot` (the watchdog's reuse is a named exception for a unit that sends alerts, not a
  precedent for a service that accepts requests). No membership in `aleix`.
- **15.0 handover:** if the endpoint needs the helper's socket, that is **a socket-unit decision
  with its own ADR, not a `usermod`** (§6.1 is that decision).
- **ADR-034 §5** — the endpoint forwards `role`; it never names a model or provider; hints are
  carried, never used to select.
- **ADR-034 §11** — identity and origin are attached by the runtime; a request body claiming them
  is refused.
- **ADR-035 §4** — the `homelab` adapter has the same shape as the fake; `Request` and `Result`
  are not extended with a backend concept to make it work. If they must change, that is a finding
  and an ADR, not a convenience.
- **ADR-039** — the endpoint forwards only what the client selected (`question`, `context`); it
  adds nothing from logs, journals, config or files. Provenance for `context` items is carried
  through as-is; assembling context is 23.2's.
- **ADR-033 §5** — no metered call. The helper's `metered` refusal stays in force.
- **ADR-025 §10 / Phase 09** — model output is never dispatched. Re-proved, not changed.
- **ADR-046 §2 / 18.2 item 3** — the side that always works lives on root; the endpoint's own
  state is on root (§6.3) and it must not carry the volume-dependent contract.
- **Phase 12/18.2 item 4** — `OnFailure=` as a drop-in with a literal alias, and the alias added
  to `homelab-notify.sh`'s `case` in the same commit.
- **Two SSH aliases** — a forward for the endpoint, if the MacBook needs one for a client probe,
  goes as a second `LocalForward` under `homelab-workbench`, never under `homelab`.
- **Runbook rule** (Phase 13): print before wait; no `sudo … | tail/head/grep` unless `sudo -v`
  ran first.

## 6. Decisions still open

Each resolved in execution, recorded in the stage report and the handover, and where marked as an
ADR. Recommendations are the orchestrator's; overturn with an OBSERVED reason.

**6.1 How the endpoint reaches the model helper — ADR required.** The socket is
`aleix:homelab-bot:0660`. Options: (a) run the endpoint as `homelab-bot` — rejected above; (b) add
the endpoint's account to `homelab-bot`'s group — a `usermod`, forbidden by the 15.0 handover
because it makes a group mean two things; (c) **introduce a `homelab-model` group owning the socket**
(`SocketGroup=homelab-model`), with `homelab-bot` and the new account as members, `0660` unchanged.
**Recommendation: (c)**, as **ADR-048 — the model socket's consumers are a group**. It is the
minimal change that keeps the Phase 09 property (the caller cannot name a program) and makes the
next consumer a group membership with a `# WHY`, not a new mechanism. The helper's `# WHY` on
`SocketGroup` is updated in the same commit. Test: `homelab-bot` and the endpoint account can
connect; `aleix`-less third account cannot.

**6.2 The endpoint's account, name and unit.** Recommendation: system account `homelab-harness`,
no shell, no home, unit `homelab-harness.service`, `User=homelab-harness`, `ExecStart` a Python
stdlib `ThreadingHTTPServer` bound `127.0.0.1:<port>` (refusing anything else in code, as
`server.py` does), `StateDirectory=homelab-harness` (on root — this is *why* no
`volume-dependent-services.md` contract: `StateDirectory=` on root adds no `RequiresMountsFor=` on
the volume), hardening set from the baseline, `RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX`
(the socket needs `AF_UNIX` — the one difference from the Workbench, with a `# WHY`), no
`LoadCredential=` (it holds no secret). Port: `8766`, next to the Workbench, recorded in the socket
table. Score target ≤ 2.0; every waiver a `# WHY`. `OnFailure=homelab-notify@harness.service` as a
drop-in; `harness)` added to the notifier's `case`.

**6.3 Where the endpoint's state lives, and what it holds.** Recommendation: `StateDirectory` on
root holds **only** `audit.jsonl` (one line per request, the fields in §4.5) and nothing that is
project content — so the endpoint is up and useful with the volume locked, and ADR-037's line
(content in the volume) is not crossed by a service on root. **Results are the client's to record**:
the Workbench writes its `ops/` records as it does today; the endpoint returns and forgets. This
keeps ADR-034 §12 (durable state is explicit, in Factory definitions, `ops/` or Brain) and means
ADR-047's trigger 3 (a service needing the volume) does not fire. If execution finds the endpoint
must persist request content, stop and say so — that reopens the account question, per the 18.2
handover.

**6.4 The taxonomy (layer 2).** Recommendation, closed and deterministic:
`question` (one bounded ask, one answer — the only class served in 23.0), `task` (needs
decomposition or tools — **refused here** with `kind: "needs_decomposition"`, addressed to 23.1),
`command` (an operational verb the bot already owns — refused with `kind: "not_a_request"`, the
client should use the bot), `unclassifiable` (routes to `question` **only if** the client declared
it a question; otherwise refused with `kind: "unclassifiable"`). Classification uses the client's
declared `kind` plus cheap structural rules (length, presence of an explicit tool/capability
request, imperative verbs from a short list); **no model call for classification** in this
sub-phase — the target architecture allows one but says it must be the smallest spend, and there
is no governor yet to bound it. Record the rules in the guide as a table; a reader must be able to
predict the class of a request by hand.

**6.5 What the audit line holds — and what it must not.** Recommendation: `request_id`, `ts`,
`client` (from origin, not body), `peer` (uid if the transport gives it; for loopback TCP it does
not — record `null`, not a guess), `kind_declared`, `class`, `role`, `unattended`, `outcome`
(`ok` / the refusal kind), `provider`/`model` when the helper reports them, `cost` (always `null`
for subscriptions — ADR-033 keeps unknown unknown), `duration_ms`, `question_len`, `context_items`,
`output_len`. **Never** the question, context, output or summary text. This is the same discipline
as 15.0's `summary_len`, applied to every field with content.

**6.6 The Workbench→homelab adapter and the action that calls it.** Recommendation: `homelab.py`
maps `Request` → endpoint request (`kind: "question"`, `role: agent_role`, `question:
instructions` prefixed by `task_summary`, `context: context`, hints through) and endpoint response →
`Result` (`refused`/`reason` from the endpoint's refusal kinds; `model` from the helper's reply;
`cost: None`). Adapter chosen by **one** configuration key in the project's `ops/project.json`
(`"adapter": "fake" | "homelab"`, default `fake`) with the endpoint URL fixed in the adapter, not
configurable per project (loopback is not a choice). The smallest action: a `workbench.cli run
<work-item-id>` subcommand that builds a `Request` from the item, calls the configured adapter,
records a `Result` on the item, and writes the audit line the Workbench already writes for actions.
**No dashboard button** — the CLI is enough to run the §8.1.3 check and keeps the web surface
unchanged. Factory-side changes are commits in `TelesforoAleix/factory`, referenced by hash in the
handover; the node's clone is updated by `git pull` in the runbook (the Workbench never pulls).

**6.7 The Telegram bot as a client.** Recommendation: **defer**, recorded with the reason. `/ask`
works and is the owner's recovery path when the volume is locked; routing it through a new service
adds a failure mode to the one component ADR-046 says must always come back, for no capability gain
in this sub-phase. 23.1 or 23.3 re-decides when the endpoint has something the bot cannot do
directly. The handover names this by phase.

**6.8 Routes for the Factory roles.** The helper refuses unknown roles; the Workbench will send
eight. Recommendation: **one route per role that the §8.1.3 check exercises** (at least one), plus
`owner-interactive` untouched, all to the same `claude/haiku, codex/mini` list — added to the
node's root-owned `config.json` in the runbook with `.bak-<date>`. Do not add a wildcard route;
"unknown role refused" is a 15.0 property under test. Roles not exercised are not added; the
handover lists which exist and which are routed.

**6.9 `RuntimeMaxSec` (15.0 debt).** Recommendation: **take it** — `RuntimeMaxSec=270` on the
helper's instance unit (2 × 120 + 30) via drop-in with `# WHY`; measured under the baseline (score
before/after); the endpoint's own client timeout to the helper is `280 s` so the endpoint outlives
the helper and reports the helper's failure rather than its own. Prove with the 15.0 fixture, not a
real double timeout.

**6.10 How a request proves it did not carry identity.** ADR-034 §11 says the runtime attaches
identity. Recommendation: the request schema has **no** `client`, `user`, `origin`, `peer` or
`request_id` field; any of them present is refused by name (the 15.0 pattern). The endpoint sets
`client` from a per-client token? **No** — no credentials in 23.0. `client` is the value the
adapter *declares* in a header, recorded as `client_declared`, and the audit line says so. A real
client identity is 23.3's (identity as harness machinery). Say plainly in the guide that in 23.0
`client` is a label, not an identity, so nobody later reads the audit line as authenticated.

## 9. Security considerations

- **The endpoint is the first service that accepts requests from another process.** Its account is
  the boundary: no `aleix`, no `docker`, no `sudo`, no home, no shell, no credential. What a
  compromised endpoint can do is: call the helper as one more consumer (capped), and write its own
  audit file. Say that in the ADR and the guide.
- **`client` is a label in 23.0.** §6.10. Nothing authenticates a client; loopback is the trust
  boundary and every local process is trusted equally. That is ADR-038 §2's model and 23.3's job to
  refine — the guide must not let the audit line read as authenticated.
- **Nothing new leaves the machine.** The endpoint forwards what the client selected to the helper,
  which sends it to the same two CLIs as today. Test 3's audit assertion and a `question`-string
  grep on the endpoint's journal prove the endpoint itself retains no content.
- **The classifier is not a security control.** It refuses classes this sub-phase cannot serve; it
  does not sanitise. A `question` containing a tool-shaped string reaches the model as text and its
  output comes back as text (test 7) — ADR-025 §10 unchanged.
- **The `SocketGroup` change widens the helper's consumers by one account.** ADR-048 records it;
  test 18 proves the group is still a boundary; the helper's per-provider caps are the shared
  budget, and the endpoint's calls count against them — which is why §6.7 keeps the bot's `/ask`
  independent for now.
- **Boot-class unit** — `safe-changes-headless.md`, second idle session, console available for row
  12's reboot.
- **No secret in either repository.** Nothing here has one.
