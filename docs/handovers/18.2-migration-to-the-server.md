## 1. Purpose

ADR-038 decided that every component runs on the reference node, inside the encrypted volume, and
that the MacBook is a client and a terminal. Phase 18.1 built the volume. Nothing is in it yet except
the probe's file. This phase moves the four layers — `brain`, the projects, Factory and the
Workbench — into the volume and runs the Workbench from there, reached from the MacBook through an
SSH tunnel.

It was split from 18.1 on 2026-09-11 (ADR-045) because the risk profiles differ: 18.1 was an offline
filesystem operation that could destroy data; this phase moves repositories that already have
remotes. Nothing here is unrecoverable. Every clone can be re-cloned; every mistake is a `git` mistake
with a remote to fall back on.

The phase is deliberately narrow. It does not build the harness endpoint (23.0), does not harden
the node (13), does not design a backup path for volume contents unless it finds one is needed, and
does not touch the watchdog.

## 3. Learning objectives

By the end, the owner should understand: why "clone, don't copy" is the whole migration and what it
means for backup (the remote is the backup, until something on the node is not in a remote); how a
systemd unit is tied to the volume's presence by contract — `ConditionPathIsMountPoint=`, `PartOf=`,
`WantedBy=homelab-data.target` — and why *the watchdog must never carry those same directives*; why
a loopback-bound service reached by an SSH `LocalForward` is a stronger position than a tailnet-bound
service with its own login, and what would justify taking the weaker one (ADR-038 §4); what a
node-side SSH key to GitHub is, what it can and cannot do, and why it is a secret on the node that
Phase 13 and Phase 14 both need to know about; and why "every listening socket accounted for and
bound to a stated interface" is the rule that replaced "no listening sockets" (ADR-038 §5).

## 4. Functional objectives

1. The five repositories are cloned into `/srv/homelab` on the node, from their remotes, with a
   node-side SSH key that can pull all five and push to the three private ones. Ownership and layout
   inside the volume are decided and recorded (§6.1).
2. The Workbench runs on the node as a systemd service, as a non-root account, binding
   `127.0.0.1:8765` only, tied to the volume by the 18.1 pattern. It replaces
   `homelab-data-probe.service` as the canary, and the probe is removed.
3. The owner opens `http://127.0.0.1:8765/` in the MacBook's browser through an SSH tunnel that
   `ssh homelab` establishes automatically (`LocalForward` in `~/.ssh/config`), and can perform a
   real Workbench action against a real project record on the node.
4. Workbench started while the volume is locked refuses with a reason in the journal, leaves no
   failed unit, and starts on unlock (ADR-038 validation 3).
5. `ss -tlnp` accounts for every listening socket by name and interface; the Workbench is not
   reachable from the MacBook over the tailnet directly — proved by attempt.
6. `docs/standards/volume-dependent-services.md` exists and states the contract, including what the
   watchdog must not carry.
7. The MacBook's clones remain as working copies. Nothing runs from them. The owner's day-to-day
   editing path (VS Code Remote SSH into `/srv/homelab/...`) is documented and exercised once.

## 5. Decisions already fixed

**ADRs:** ADR-037 §5 (everything in the volume), ADR-038 (placement: node hosts everything, harness
and Workbench on loopback, SSH tunnel, socket accounting rule), ADR-035 §7 (local Workbench needs no
application login — the OS user boundary is the boundary), ADR-036 §5 (Workbench loopback-only,
enforced in `workbench/server.py`), ADR-041 (safe-changes-headless), ADR-043 (the volume-dependent
service pattern is shared by 12, 18.2, 23), ADR-045 (this phase's existence and scope), ADR-046 §3
(nothing outside the unlock path holds key material for the volume), ADR-030 (the four-layer
workspace and repo visibility).

**Inherited from Phase 18.1, by name (handover §Phase 18.2):**

1. The volume as built; 18.2 decides ownership and layout.
2. Never allocate the last extent. Growing is online: `lvextend` → `cryptsetup resize` → `resize2fs`.
3. The service pattern, proved twice: `ConditionPathIsMountPoint=/srv/homelab`,
   `PartOf=homelab-data.target`, `WantedBy=homelab-data.target`, `After=`. `Condition`, not `Assert`.
   **`systemctl start` of a skipped unit returns 0** — check `is-active`, never `start`'s exit code.
   The probe is the reference implementation; this phase's first real service replaces it and removes
   it, saying so.
4. Workbench must refuse to start while locked — this pattern is how, proved with refusal *and*
   control.
5. Docker's `data-root` is on unencrypted root. Decide; ADR only if it moves.
6. `/srv/homelab` is immutable underneath. Never `chattr -i` it to make something work.
7. Backup scope: configuration is covered, contents are not. This phase says whether the remotes are
   enough.
8. Re-take the LUKS header backup if any keyslot changes. Confirm the existing one is on the card
   before relying on it. This phase changes no keyslot.
9. Write `docs/standards/volume-dependent-services.md` before a second service copies the pattern.
10. Any runbook step that boots rescue media says what the media is for. None expected here.

**Inherited from Phase 12, by name (handover §Phase 18.2):**

1. The watchdog/notifier depends on nothing this phase changes.
2. **Do not add `ConditionPathIsMountPoint=`, `Requires=`, `After=`, `Wants=` or `PartOf=` naming the
   volume, `homelab-data.target`, the probe, or the bot to `homelab-watchdog.service` or `.timer`.**
   A locked volume would then skip the one unit whose job is to say the volume is locked.
3. Re-verify before the brief is committed: `systemctl is-enabled homelab-watchdog.timer` →
   `enabled`; `systemctl show -p After,Requires,Wants,PartOf,ConditionPathIsMountPoint --value
   homelab-watchdog.service` → no `srv`, `homelab-data`, or bot; `journalctl -u
   homelab-watchdog.service -b` → one run, one of the four literal messages.

**Scope rule (ADR-017):** cross-phase changes are ADRs carried forward, never applied silently. This
phase does not modify the bot, the model helper, the watchdog, the firewall, sshd, or the volume's
keyslots.

## 6. Decisions still open

Each is resolved by the execution stage, recorded in the stage report and the handover, and — where
marked — as an ADR.

**6.1 Who owns the volume's contents, and the layout.** Recommendation: a single layout mirroring
the MacBook so paths transfer mentally —

```
/srv/homelab/
  homelab/            TelesforoAleix/homelab       public
  factory/            TelesforoAleix/factory       public
  projects/oncla/     TelesforoAleix/oncla         private
  projects/factory/   TelesforoAleix/factory-ops   private
  brain/              TelesforoAleix/brain         private
```

owned `aleix:aleix`, mode `0750` on `/srv/homelab` itself (root-owned directory, group `aleix`, or
owned by `aleix` — execution decides after checking what `chattr +i` on the mountpoint permits;
the immutable bit is on the *underlying* directory and does not constrain the mounted filesystem's
root). Rationale: the Workbench runs as the account that owns the repos so `gitops.py` can commit;
`aleix` is the account the tunnel lands as; a second account would need its own key and its own
repo ownership for no boundary gain today. The alternative — a dedicated `workbench` account owning
the projects, `aleix` as a member — is the right shape once a second person or an automated client
exists (23.0's endpoint runs as its own account and reaches the Workbench over loopback, not over
the filesystem). Record the choice; if execution picks the dedicated account, say why.

**6.2 The node-side GitHub key.** Cloning private repos and pushing from the node needs a key on
the node. Recommendation: one new ed25519 key generated on the node (`~aleix/.ssh/id_ed25519_github`,
passphrase-less because a service commits with it, `0600`), registered as an **SSH key on the owner's
GitHub account** with the title `homelab node — 2026-09-12`, not as per-repository deploy keys —
GitHub does not allow one deploy key on several repositories, and five keys is five things to revoke.
The MacBook's key does not move to the node. This is a new secret on the node that grants write to
the private repositories: named in §9 and handed to Phase 13 by name. The alternative (a fine-grained
token in a credential helper) trades a file for a token with an expiry; not taken unless the key
approach fails. **Never `git remote -v` to verify a remote — `git ls-remote`** (the workspace memory's
hazard about the `brain` rename redirect stands).

**6.3 How the Workbench is run.** Recommendation: a system unit `homelab-workbench.service`,
`User=aleix`, `WorkingDirectory=/srv/homelab/factory`, `ExecStart=/usr/bin/python3 -m workbench.cli
--project /srv/homelab/projects/factory serve`, the 18.1 pattern for the volume, hardening in the
spirit of the bot's unit (`NoNewPrivileges`, `ProtectSystem=strict` with `ReadWritePaths=` on the
volume, `RestrictAddressFamilies=AF_INET AF_INET6` — **no AF_UNIX**: S1 observed by reading
`workbench/engine.py` that the served Workbench never invokes `git` or `gitops.py`, so it needs
neither an SSH agent socket nor any UNIX socket; `SSH_AUTH_SOCK` is unset on the node in any case),
`Restart=on-failure` with a bounded start limit, and an `OnFailure=homelab-notify@workbench.service`
drop-in in the Phase 12 pattern. `MemoryDenyWriteExecute=yes` is in the bot's set but unproved
against Python 3.14 on this node; S2 proves each directive with `systemd-run` before the unit is
written, and drops any Python 3.14 does not tolerate, saying why. `--project` names the
`factory-ops` workspace because it is the project the Factory operates on; the alternative is `serve`
per project, which is a later need. **The workspace must be Workbench-initialised**
(`ops/project.json`) or `serve` refuses at start — S1 found `factory-ops` was not; fixed by one
`workbench.cli init` commit in `factory-ops` (S2 step 0), proved additive on a scratch copy first.
Not a user unit: user units die with the session unless lingering is enabled, and lingering is a
second mechanism for what a system unit does directly.

**6.4 PyYAML.** The Workbench's only dependency (`requirements.txt`: `PyYAML>=6.0`). **Nothing to
install:** S1 observed `python3-yaml 6.0.3-1build1` already present on the node, auto-installed as a
dependency of `netplan.io` and `cloud-init-base`; `apt-cache policy` shows the archive's candidate is
the same version. The one action is `sudo apt-mark manual python3-yaml` (owner, done 2026-09-12) so
a future autoremove of its dependers cannot take the Workbench's only dependency with it. Not
`pip`, not a venv. Recorded in §14 and the tested-versions table as 6.0.3.

**6.5 Docker `data-root`.** Recommendation: **leave it on root.** Nothing in Docker holds project or
knowledge content today; moving it makes Docker wait on unlock for no content it protects. Record the
decision in the handover; no ADR because nothing moves. Revisit trigger: the first container that
holds content from the volume bind-mounts it from `/srv/homelab`; if a container ever needs its own
persistent content, that is the ADR.

**6.6 Backup scope for volume contents.** Recommendation: **the remotes are the backup for the
clones** — every repository is cloned from its remote and can be re-cloned. **They are not the
backup for what the Workbench writes.** S1 observed, by reading `workbench/engine.py`, `server.py`
and `cli.py`, that the served Workbench writes records into `<project>/ops/<collection>/` and
appends to `ops/audit/audit.jsonl`, and **never commits or pushes** — `gitops.py` is called only by
`acceptance/synthetic_project.py`. Those writes sit uncommitted on the node until the owner commits
and pushes by hand. The handover names `/srv/homelab/projects/factory/ops` (uncommitted records and
`audit.jsonl`) as **Phase 14's problem, by name**, OBSERVED not assumed. `backup-node.sh` gains the
new configuration files (§10), not the contents.

**6.7 Whether the MacBook's clones are removed.** No. They stay as working copies; the phase's
deliverable is that nothing *runs* from them. The owner's editing path becomes VS Code Remote SSH
into `/srv/homelab/...` (already in use for the node — `docs/reference/software-stack.md`), with
`lab.code-workspace` on the MacBook untouched. Recorded, not enforced.

`systemd-analyze security` recorded. Enable via `homelab-data.target`, not `multi-user.target`.

**7.7 Replace the canary.** Once `homelab-workbench.service` is proven (7.9), remove

**7.8 The tunnel.** Add to `config/ssh/homelab.ssh-config.example`, under `Host homelab` only (not

```
    # Phase 18.2: the Workbench binds loopback on the node; this is the only door.
    LocalForward 127.0.0.1:8765 127.0.0.1:8765

```

The owner applies it to `~/.ssh/config`. `ExitOnForwardFailure` because a silently failed forward
looks exactly like a Workbench that is down.

**7.9 Validation runs (§8)** — refusal, control, tunnel, socket accounting, watchdog unaffected.

**7.10 Docs (§11, §12) and handover (§16).**

**Boot-class and remote-access changes:** 7.6 (a `WantedBy=` on a boot target), 7.7 (removing a

## 9. Security considerations

- **A new secret on the node:** the GitHub SSH key (§6.2), passphrase-less, write access to three
  private repositories. Its blast radius is the private repositories' contents and history, not the
  node. Mitigations this phase: `0600`, owned by `aleix`, named in the handover for Phase 13
  (revocation is one click on GitHub; the key title says which node) and for Phase 14 (it is not in
  `backup-node.sh` by design — a restored node generates a new key). It is **not** committed, not
  in `config/`, not in any example file.
- **The Workbench has no login.** The boundary is: Tailscale authenticates the device, sshd
  authenticates the key, the tunnel lands as `aleix`, loopback is unreachable from any interface.
  The `LocalForward` binds `127.0.0.1` on the MacBook side too, so nothing on the MacBook's LAN can
  reach the forwarded port.
- **Network exposure:** one new listening socket, loopback. `ufw` unchanged. ADR-038 §5's rule
  becomes the measured statement in row 8.
- **Destructive operations:** none on data. Removing the probe unit is a unit removal, not data.
  Cloning writes into an empty volume. No `rm -rf`, no `chattr -i`, no keyslot change.
- **Privilege:** the Workbench runs as `aleix`, which is the sudo-capable admin account. The unit's
  `NoNewPrivileges=yes` keeps the service itself from escalating; this is the accepted shape until
  §6.1's dedicated account is warranted, and the handover says so to Phase 13 by name.
- **Volume contents are private repositories.** The volume is the control (ADR-032, ADR-037). The
  node's root filesystem still holds nothing from them.
- **Headless:** §7's boot-class and remote-access steps under ADR-041.

**Open risks and unsatisfied controls, not to be silently inherited:**

- **Nothing pushes at all.** The served Workbench never commits (§6.6, OBSERVED in S1); its `ops/`
  writes and `audit.jsonl` diverge from the remote from the first action until the owner commits and
  pushes by hand. "The remote is the backup" is false for that window, and the window is open-ended.
  An earlier draft of this risk assumed `gitops.py` pushed and worried about silent push failure;
  that failure path is loud (`GitError` with stderr) and, from the service, unreachable. Whether the
  Workbench should commit its own writes is a finding for the `factory` repository, not fixed here.
- Two clones of every repository now exist (MacBook and node). Divergence is an ordinary git
  problem, but the owner has not worked that way before. Recorded as a practice, not a control.
- Row 9 (lid closed) proves the MacBook is not a host; it does not prove the node survives the
  *Tailscale* connection dropping mid-action. Not tested; not blocking.
- The `LocalForward` line is in the example file, applied by hand. A second MacBook or a rebuilt one
  must reapply it; the guide says so.
