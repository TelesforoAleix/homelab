## What the next phase inherits

### Phase 15.1 — metered provider and spend governor — by name

Brief §16 items 1–5, then the fields you fill in.

1. **Exactly what a provider entry and a model entry look like.** Copy and edit:

   ```json
   "gateway": {
     "bin": "/absolute/path/or/whatever-the-integration-needs",
     "unattended": true,
     "metered": true,
     "credential": "ai-gateway-key",
     "models": {
       "cheap": { "id": "<vendor model string>", "note": "why this one" }
     }
   }
   ```

   A **provider** is a key in `providers` whose name is in `providers.py`'s `BY_NAME` — adding one
   is code, by design (ADR-026 §2). It carries `bin` (absolute), `unattended` (required boolean),
   `models` (non-empty), and — for you — `metered` and `credential`. A **model** is a key under
   `models` (the alias routes use, `^[a-z0-9][a-z0-9-]{0,31}$`) with `id` (the only string that
   ever reaches argv, and only from here) and `note`. A **route** is `"name": ["provider/model", …]`,
   order = fallback order; validated at load against the registry.

   **The helper today refuses to load a config in which `metered` or `credential` is present**
   (`helper.py` `load_config()`, the loop over `("metered", "credential")`). This is deliberate and
   the reasoning is the orchestrator's: an inert field is how a paid call happens without a
   governor — someone sets it, it appears to work, and nothing meters. **You remove that refusal in
   the same commit that ships the governor**, not before. `credential` is a *name* the unit resolves
   through `LoadCredential=` (baseline §4: `/etc/homelab-model-helper/<name>`, `root:root 0600`);
   it is never a path and never on the wire. **You owe ADR-046's table a row** for the gateway key
   with the provider console where it is revoked, in that same commit.

2. **How eligibility was proved, including the fixture.** `services/model-helper/fixture-tests.py`.
   The fixture is `config.example.json` with exactly three substitutions (both `bin` → a stub shell
   script that prints `STUB-ANSWER` and honours codex's `-o FILE`; `state_file` → a temp path;
   `unattended` → the value under test), asserted to have the same recursive key set as the example
   — so a format change fails the fixture loudly instead of testing a stale shape. `helper.py` is
   driven the way systemd drives it (one JSON line on stdin; it has no socket code), so the real
   loader, router, eligibility check, `Limiter` and provider argv code run. Test 8 and the hint
   check require the error to **name the field**; test 3 counts only if test 1 refused on the
   reason. OBSERVED: 19/19 on the MacBook (four runs), 19/19 on the node as `aleix` from `/opt`
   under `install-model-helper.sh verify`. For a metered provider you add a stub for its
   integration the same way; the `unattended: false` fixture already covers the refusal path for
   any provider.

3. **The unattended budget: `owner_reserve = {per_hour: 3, per_day: 15}` of `{6, 30}` — half.**
   A **floor**, not a lower cap (brief §6.6, ADR-026 §6): unattended calls may reserve only while
   the provider's count is below `cap − reserve`; the last `reserve` calls in each window belong to
   the owner. **One count per provider, keyed as the caps are** (`Limiter`, `calls.json`, format
   unchanged) — the reserve is a lower ceiling on the same count, not a second scheme. Half because
   the owner's `/ask` and `/status` are what the floor protects and nothing unattended exists yet
   to justify more; it is config (`caps.owner_reserve`), tune it there. The refusal text names it:
   `claude: unattended daily budget reached (15/15, 15 reserved for the owner)`. **Your governor's
   attended/unattended split (ADR-033 §5) is this same idea over money and four windows** — build
   it beside `Limiter`, not by widening `Limiter` to know about cost.

4. **Fallback does not cross routes.** Refused (brief §6.4). `handle_ask` walks the route's own
   list; an exhausted route is `kind: "exhausted"`. A cost-aware cross-route fallback is yours to
   decide with prices in hand, not designed blind here.

5. **What still blocks Phase 15 proper.** The provider is chosen (ADR-033). What remains is your
   integration with the governor. The registry already accommodates: the provider entry shape,
   `metered`, `credential`, `unattended` per provider, routes with an order, distinguishable
   refusals (`ineligible` / `unknown_role` / `exhausted` / `error`), and hints on the wire that are
   logged and provably do not select (test 11). You must still add: the provider class in
   `providers.py`, the governor (four windows, attended/unattended, fail-closed, persistent),
   `LoadCredential=` in the unit (**a unit change — measure the score before and after, baseline
   §2; today 3.8**), the ADR-046 row, and the removal of the presence refusal.

### Phase 23.0 — the endpoint — by name

The wire protocol as it stands, from `services/model-helper/README.md`:

| Field | Honoured or logged only |
|---|---|
| `v`, `op`, `user_id`, `question`, `context` | Honoured (Phase 09) |
| `role` | **Honoured — the only field that selects anything.** A lookup key into `routes`; absent → `default_route` (`owner-interactive`); unknown → `kind: "unknown_role"`, no cap spent |
| `unattended` | Honoured: default `false`; `true` triggers the eligibility filter and the owner floor |
| `summary` | Logged as a **length** only (≤ 200 chars) |
| `priority`, `severity`, `complexity` | Logged (closed enums); **never select** — test 11 proves the same `provider/model` with and without them |
| anything else | **Refused by name** (`unknown field 'model'`) |

The router is **deterministic with no AI-assisted path** (ADR-034 §5: starts deterministic, kept as
the fallback). `resolve_route(cfg, key)` in `helper.py` is the whole of it and receives the key
alone. When you send a role, it must exist in `routes` in the node's root-owned `config.json` —
adding a route is a config change on the node, not a code change. The socket is unchanged:
`/run/homelab-model-helper.sock`, `aleix:homelab-bot:0660`, `AF_UNIX`; your endpoint runs as its own
account (ADR-047) and does **not** get the socket's group — if 23.0 needs the helper, that is a
socket-unit decision with its own ADR, not a `usermod`.

## Security notes

- The caller still cannot name a binary, path or model — and now cannot *send* such a field
  either (test 8). `role` is a lookup key; `id` is the only string reaching argv and comes from
  root-owned config.

  control against this project forgetting what a scheduled caller implies. Recorded in the guide.
- Caps are capacity, not billing. `Limiter` was deliberately not taught about cost.

## Problems / failures / lessons

Per PROJECT.md §11:

1. **Fixture tests passed vacuously on first run.** Tests 8 and 11b accepted *any* error, so a
   broken config would have "passed" them; test 3 accepted a counter at zero for any reason →
   noticed on the S1 run against the old code, where "helper misconfigured" satisfied them →
   tightened to require the message to name the field, and test 3 to depend on test 1's reason.
   The brief's warning about confident negatives applied to the test of the test.
2. **`verify` on the node said UNKNOWN**: `fixture-tests.py` reads `config.example.json` beside
   itself and the installer never copied it to `/opt` → the check reported UNKNOWN rather than a
   verdict, which is the right failure → installer now ships the example; re-run passed.
3. **The installer's own probe landed in the swap window.** `install` runs `verify` before the
   runbook's `mv`, so its probe hit new code + old config, got `helper misconfigured`, exited 1, and
   left one `homelab-model-helper@…-999.service` failed (plus one `OnFailure` notice) → the window
   the runbook described as real was observed, caused by the runbook itself → step 3b
   (`reset-failed`) added; recorded rather than reordered, because the honest order is install →
   mv and the probe is worth having.
4. **Runbook step 0 first claimed "the old verify passes"** — but the file just copied *is* the new
   verify → corrected before hand-over to "six ok + UNKNOWN + FAIL, expected".
5. **Runbook had two `sudo … | grep` lines**, the Phase 13 closing defect's shape → `sudo -v` as
   the first line of step 0 (orchestrator's alternative), greps kept.
