## Outcome

**Complete.** The node has **32 GB** — 2 × 16 GB Kingston `KVR26S19D8/16` in ChannelA-DIMM0 and
ChannelB-DIMM0, configured at 2133 MT/s (the CPU's ceiling), dual-channel. Proved by `dmidecode`,
`free` (30 GiB), a full `memtester 20G 1` loop (16 tests `ok`, 2 h 07 min) and a kernel log free
of MCE/EDAC lines; boot, Wi-Fi, the watchdog notice, the data-volume unlock and every service
returned as before. Cost 700 DKK. The 8 GB module is kept as a spare.

## What the next phase inherits

- **Verified starting state:** 32 GB as above. Re-verify with `free -h` (30 GiB) and
  `sudo dmidecode -t 17` (two 16 GB devices, both channels). `systemctl is-system-running` →
  `running`, no failed units, all four Home Lab units active, volume unlocked, Workbench active at
  22:14 UTC 2026-09-14.
- **A spare 8 GB module** (Samsung `M471A1K43BB0-CPB`, DDR4-2133) exists, in an anti-static bag
  with the owner. It is the rollback for a memory fault and nothing else.
- **Swap unchanged** — 4 GB swapfile, never used, `vm.swappiness = 10`. Revisited and left alone
  (`hardware.md` §Swap). Not a debt.
- **Open risk — a stall of ~3 minutes drops the node's address.** The shared building network's
  DHCP server issues 3-minute leases (`LIFETIME=3min`, `T1=1min 30s`). Under `memtester` the
  renewal failed and `systemd-networkd` removed the address, twice, reproducibly; the Wi-Fi
  association held. Nothing on the node was changed in response. **Phase 14** should treat lease
  length as part of "reachable"; the gateway is not ours (2026-09-10 reassessment), so the answer,
  if any, is on the node's side — and is a lockout-class change under `safe-changes-headless.md`.
- **Operating rule, from experience:** memory-stress tests are run from the console. Recorded in
  `hardware.md` and `software-stack.md`.
- **Unsatisfied controls:** none. No ADR required anything of this phase.
- **Decisions not to inherit silently:** none. ADR-001/002/016/041 are unchanged.
- **Ground already covered:** the first observed classification of a `poweroff` by the Phase 12
  watchdog — `clean reboot. Down ~41m` — closing the "`systemctl poweroff` path untested" residual in
  project-state's Phase 12 status. The first POST after a memory change took 17.0 s (was 5.7 s);
  whether it settles back is for the next boot to show.
- **Still pending, by name (Phase 13):** the firmware update `fwupdmgr` reports. Not applied here,
  by decision (brief §5).
- **Owner close-out done 2026-09-15:** `memtester` removed (verified: `dpkg -l` shows no package,
  `/tmp/memtester.log` gone); `software-stack.md` row now reads Removed. Console session closed;
  monitor and keyboard detached.

## Security notes

The machine was opened with the adapter unplugged. No BIOS setting was entered or changed; the
supervisor password was not needed. No new listener, account, credential, group or dependency
(`memtester` is temporary and holds nothing). The only exposure created was the ten-minute network
outage the first test caused — recovered from the console, as ADR-041 intends.

## Costs

## Problems / failures / lessons

Three, in the build log: the cover that would not close; the stability test that took the node off
the network (root-caused to 3-minute DHCP leases under load — not the memory); the console not
attached for the first boot, then needed twenty minutes later.
