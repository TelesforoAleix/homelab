## 1. Purpose

The node has run on a single 8 GB module since purchase. `hardware.md` said the upgrade "should be
driven by observed pressure from real services rather than by reaching a round number". The node now
runs the Telegram bot, the model helper, the harness, the Workbench and Docker, with the knowledge
layer (Phase 10.x) and the remaining harness sub-phases queued behind them — and the owner has bought
the modules. This phase installs them, **proves** the result on Linux, and updates every file that
states the installed configuration. It does not mark anything complete before the checks pass.

## 2. Starting state

Verified from the repository (Phase 01 Part A and later, `hardware.md`):

| Fact | Value |
|---|---|
| RAM | 1 × 8 GB Samsung `M471A1K43BB0-CPB`, DDR4-2133, in ChannelA-DIMM0; ChannelB-DIMM0 empty |
| CPU memory ceiling | i5-6600T: DDR4-2133, two channels |
| Platform ceiling | two SO-DIMM slots → 32 GB |
| Swap | 4 GB swapfile, `vm.swappiness = 10` |
| Boot | 27.9 s (firmware 13.81 s); `is-system-running` → `running`; 0 failed units |
| Data volume | locks at power-off; watchdog reports `LOCKED`; `sudo data-volume.sh unlock` |
| Console | detached; connectors present; login tested (ADR-041) |
| Firmware | FWKT63A 2016-12-08; `fwupdmgr` reports an update — **not in scope** |

The live before-state is captured in the build log before the machine is powered off.

**The parts:** 2 × 16 GB Kingston ValueRAM `KVR26S19D8/16` — DDR4-2666, 2Rx8, 260-pin SO-DIMM,
1.2 V, non-ECC, unbuffered. The CPU tops out at 2133 MT/s, so the modules are expected to run at
**2133**, not 2666. That is the platform, not a fault.

## 3. Learning objectives

- How the M700 Tiny opens and where its memory lives (under the storage-drive bracket — Lenovo HMM
  ch. 9), and what else is disturbed on the way (the Wi-Fi antenna, the SSD's SATA seat).
- How to prove a memory change on Linux rather than trust the box: `dmidecode` types 16 and 17,
  `/proc/meminfo`, the kernel log for MCE/EDAC, and an in-OS stability test.
- Why "the module says 2666 and the system says 2133" is correct.
- What a power-off (not a reboot) looks like to the Phase 12 watchdog — never observed until now.

## 4. Functional objectives

1. Both new modules installed, the old module removed and kept as a spare.
2. The system detects **32 GB**: two 16 GB devices, one per channel, configured at 2133 MT/s.
3. A memory-stability test passes with no MCE/EDAC lines in the kernel log.
4. Boot, Wi-Fi, the watchdog notice, the data-volume unlock and every service come back as before.
5. Every file stating the installed configuration is updated — after 2–4, not before.

## 5. Decisions already fixed

- ADR-001 (used-hardware reference build), ADR-002 (the M700's role — this does not make it an
  inference machine), ADR-016 (Wi-Fi is the reference link — the antenna is the only path in),
  ADR-041 and [`safe-changes-headless.md`](../standards/safe-changes-headless.md) (a power-off with
  the box open is physical access by definition; the console is attached for first boot).
- The BIOS is not changed. Secure Boot, boot-order lock, PXE-off and the supervisor password stay
  exactly as Phase 13 left them.
- The firmware update `fwupdmgr` reports is **not applied** here (Phase 13 handover).
- Pass gate: **`memtester` in Ubuntu**, not an offline memtest86+ run (owner decision 2026-09-14).

## 6. Decisions still open

- Whether `memtester` stays installed afterwards (default: removed, so `software-stack.md` stays a
  list of what the node runs).
- Whether the 4 GB swapfile should change against 32 GB. Expected answer: no — swap is a safety
  margin, not a proportion, and `swappiness` is already 10.

## 7. Implementation scope

Step 0 (before opening): branch, this brief, before-state capture, owner-fired `poweroff`.
Step 1 (owner, at the box): the Lenovo HMM sequence — cover screw, cover, drive bracket, modules,
reassembly, antenna reconnected, console attached.
Step 2: first boot, Telegram notice, detection checks, unlock, standard §8 close.
Step 3: `memtester 24G 1`, kernel-log scan.
Step 4: troubleshooting table, only if needed.
Step 5: documentation, guide, handover, Definition of Done.

## 8. Validation / tests

| # | Check | Pass |
|---|---|---|
| 1 | `free -h` / `MemTotal` | ≈ 31 GiB |
| 2 | `dmidecode -t 17` | two devices, 16 GB each, ChannelA-DIMM0 and ChannelB-DIMM0, Kingston, Speed 2666, Configured 2133, Rank 2 |
| 3 | `dmidecode -t 16` | max capacity 32 GB, 2 devices |
| 4 | `dmesg` / `journalctl -b -p err` | no MCE, EDAC or memory-error lines |
| 5 | `memtester 24G 1` | every test `ok`; check 4 re-run afterwards, still clean |
| 6 | `systemd-analyze` | recorded; firmware time may rise (memory training) |
| 7 | `is-system-running` → `running`, `--failed` empty, on a fresh SSH connection | as before |
| 8 | `iw dev wlp1s0 link` | link up, signal comparable to −55 dBm — the antenna went back |
| 9 | Telegram boot notice received; wording recorded | first observed poweroff→boot classification |
| 10 | `data-volume.sh unlock` → Workbench `active` | as before |
| 11 | SSD present (`lsblk`), root and VG unchanged | the bracket seated on SATA |

## 9. Security considerations

No network, SSH, authentication, boot-configuration or account change. The box is opened with the
adapter disconnected. The BIOS supervisor password is not needed and not entered. Nothing leaves the
node; no new listener, account, credential or dependency (`memtester` is temporary).
