## 1. Purpose

Give executor agents their own way onto the node — an account, a key, an SSH alias, and a closed
`NOPASSWD` command list — so that a runbook's routine steps are run and read by the agent, and the
owner does only what needs a password, a secret, a browser, a phone, or a lockout-class change.

It is small: one account, one key line, one sudoers file, one SSH alias, one backup update, and
the runbook convention written into the standard. It is also a security change to the node's
authentication layer, which is why it is a phase with a brief and an ADR rather than a line in
15.1's runbook.

**Out of scope:** any change to `aleix`'s sudo; Tailscale ACL (same port, same device); the
Telegram bot's privileged set; anything that lets the agent touch a credential, the volume's
lock state, or a lockout-class file — ADR-049 §3.

## 6. Decisions still open

**6.1 Shell for the account.** Recommendation: `/bin/bash`, because the executor runs shell
pipelines; `nologin` would force everything through `sudo` and widen the list. No password
(`passwd -l`), no `~/.profile` customisation.

**6.2 Staging directory for `install`.** Recommendation: `/tmp/homelab-agent/` created by the
agent per session (`/tmp` is cleared at boot — a feature, not a bug here); the sudoers `install`
line matches that prefix only, so a file must be staged there before it can become config. No
`install` from `/home/homelab-agent` or anywhere else.

**6.3 `journalctl` — full read or unit-scoped?** Recommendation: full read. Unit-scoped globs
in sudoers are fragile, and the journal holds no secret by the project's own rules (the Phase 13
audit and 15.1's type/code-only logging exist precisely so this is true). State in the guide
that this is a property the project maintains, not one sudoers enforces.

**6.4 Whether the agent may `restart` the bot.** Recommendation: yes — `homelab-*` includes it,
and restarting the bot is a routine step (the ADR-048 group change needed it). The bot is the
recovery path when the volume is locked, but a *restart* is not a *stop-and-leave*; a runbook
that stops it must start it in the same block, and the watchdog would notice within its interval.
`homelab-data.target` is matched by the glob too — `stop` on it unmounts nothing (the mount is
`data-volume.sh`'s), so it is harmless; note it, do not special-case it.

**6.5 The MacBook side.** Recommendation: the executor's `ssh homelab-agent` uses `BatchMode=yes`
and `ConnectTimeout=10` in the alias so a hung command fails rather than waits; no
`AddKeysToAgent` — the key is passphrase-less like the GitHub key (an agent cannot type a
passphrase either), `0600`, excluded from backup, revocable by one `authorized_keys` line.
Record it in ADR-046's table? **No** — it is on the MacBook, not on root; it is recorded in the
guide's key inventory with its revocation path instead.

## 7. Implementation scope

Two stages; one owner session; one lockout-class step.

**7.1 S1 — Files and local proof (executor, no node change).** `scripts/server/install-homelab-agent.sh`
(`install` / `verify` / `uninstall`: account, `authorized_keys` from a public key passed as a
file, the sudoers file via `visudo -c -f` then `install -m 440`, the `AllowUsers` line appended
to Phase 13's sshd drop-in **as a separate step the owner runs**); `config/sudoers.d/homelab-agent`
committed (it is configuration, not a secret); `config/ssh/homelab.ssh-config.example` gains
`Host homelab-agent`; `verify` runs every §8 allow and deny as `homelab-agent` and reports
per line; backup scripts updated; standard + safe-changes edits; guide skeleton; ADR-049 index
row. Local proof: `visudo -c -f config/sudoers.d/homelab-agent` on the MacBook (or in a
container if macOS `visudo` differs — state which).

**7.2 S2 — The node (owner session; second idle session for the sshd step only).** Owner
generates the key on the MacBook (`ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_homelab_agent -N ''`),
adds the alias, `scp`s the **public** half; on the node as `aleix`: `install-homelab-agent.sh
install <pubkey>`; then the sshd step under `safe-changes-headless.md` (second session open,
`sshd -t`, reload, `ssh -o BatchMode=yes homelab true` still works from the MacBook, then
`ssh homelab-agent true` works); then `verify` as `aleix` and the §8 rows; backup + verify;
closing check. Then — and this is the phase's proof of purpose — **the executor runs row 12
itself** over `ssh homelab-agent` and reports it OBSERVED in its own words.

**Rollback.** `install-homelab-agent.sh uninstall` (removes sudoers file first, then the
account); the sshd drop-in line removed + `sshd -t` + reload from the second session. Nothing
else changes.

## 9. Security considerations

- **This adds a third way onto the node** (owner key, second key on the card, now the agent key).
  Its blast radius is ADR-049 §2 and nothing more; §3 is the line; row 9 proves it.
- **The agent can replace `config.json` for the helper** — a money path through the governor's
  ceilings, bounded by the gateway's per-key budget ($10/week). Stated in the guide and in 15.1's
  handover.
- **The sshd `AllowUsers` edit is lockout-class.** Second idle session, `sshd -t`, third
  connection before the second is closed. A wrong edit denies `aleix` too; the console is the
  fallback.
- **The agent key is passphrase-less on the MacBook.** Same posture as the GitHub key: `0600`,
  excluded from backup, one-line revocation. A stolen MacBook session already has the owner's
  key in the agent; this adds an account that cannot lock the owner out or read a secret.
- **Sudoers is owner-only forever.** The agent cannot widen its own grant; `visudo -c -f` before
  every install; the file is committed so a diff shows any change.
- **No new listener, no new group, no credential on root.**
