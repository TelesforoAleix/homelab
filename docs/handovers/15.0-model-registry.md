## 0. Governance note

### 0.1 Why this is a sub-phase and not Phase 15

Phase 15 is "experiment intentionally with direct APIs, multiple hosted providers, unified gateways,
cost/latency/quality routing, fallbacks, and observability". **None of that can start until a metered
provider is** ~~chosen, and ADR-026 deliberately did not choose one~~ **integrated with its spend
governor** — ADR-033 (2026-09-11) has since chosen Vercel AI Gateway and made the governor a
precondition for any paid call. That integration is Phase 15.1. Nothing metered happens here.

What *can* be done now is the structural half: make models configuration rather than code, and build
the eligibility check ADR-026 requires. That is genuinely useful on its own — it turns adding a
provider later into a configuration change instead of a rewrite — and it costs nothing, because it
is proved with the two subscription CLIs that already exist.

So this is `15.0` under the roadmap's sub-phase rule, and Phase 15 proper remains open.

### 0.2 Phase 15 has already accidentally started

`services/model-helper/providers.py` is already a two-provider router with independent per-provider
limits and fallback proved against a genuinely exhausted provider. This phase does not introduce
routing. **It makes existing routing explicit and configurable**, which is a different and much
smaller claim.

### 0.3 Sequencing

~~Against Phase 18 … The node still has no backup, which is exactly what Phase 18 exists to fix.~~
**Revised 2026-09-13:** Phases 18, 18.1, 18.2, 12 and 13 are complete. The node has a verified backup,
an encrypted volume, and a written security baseline. This is a user-space service change,

The one boot-class rule that applies: the helper's unit is edited under

directive from the standard's *measured limits* list is a regression, not a hardening.

## 1. Purpose

ADR-026 decided that metered providers become the target substrate, that models become
configuration, and that every provider carries an `unattended` eligibility field the router enforces
structurally. It named no vendor and set no date.

This phase builds that structure using what is already installed, so that:

- adding a metered provider later is a configuration entry, not a redesign;
- the eligibility mechanism exists and is **proved** before anything depends on it;
- the caller stops naming a model, which is the precondition for ~~ADR-027's agents declaring a
  need~~ **ADR-034 §5: the agent's *role* is its declaration of need**. The router's input is the
  role, a bounded task summary, and validated metadata that are *hints, never selectors*. This brief
  originally said "task class"; read every remaining "task class" as **routing key**, whose value in
  the agent world is the role and whose only value today is the bot's.

## 2. Starting state

Verified by reading the installed source on 2026-09-10; unit and node facts revised from the Phase
13 handover (OBSERVED 2026-09-13).

**The unit, after Phase 13:** `homelab-model-helper@.service` runs as `aleix` — one of ADR-047's two
named exceptions, because it must read the OAuth files — with `InaccessiblePaths=-/home/aleix/.ssh`
(the GitHub push key is unreadable inside it, proved), `SystemCallArchitectures=native`, **no**
`SystemCallFilter` (`@system-service` kills the Claude CLI with SIGSYS — tried and removed, `# WHY`
in the unit), **no** `RestrictNamespaces` (codex's own sandbox needs namespaces, Phase 09 `# WHY`),
no `MemoryDenyWriteExecute` (Node JIT). `systemd-analyze security` → **3.8**, waived per finding.
Socket baseline on the node is **seven** (this brief's §8 said 6 — the Workbench added one in 18.2);
the helper's own socket is `AF_UNIX`, not in `ss -tln`. Every unit change goes through
`install-model-helper.sh` and must leave the score at 3.8 or better, each waiver still commented.

| Thing | Current form |
|---|---|
| Provider selection | `config.json` `"providers": ["claude", "codex"]` — an ordered list that doubles as fallback order |
| Provider entry | `{"bin": ..., "model": ...}` — **exactly one model per provider**, hardcoded in config |
| Provider implementations | `BY_NAME = {"claude": ClaudeProvider, "codex": CodexProvider}` in `providers.py` |
| Construction | `build_providers()` instantiates in config order |
| Fallback | `handle_ask()` iterates in order, advancing **only** on `kind == "exhausted"`; a hard error stops |
| Caps | One global `caps: {per_hour: 6, per_day: 30}`, applied **per provider** by `Limiter`, keyed on provider name |
| Cap state | `/var/lib/homelab-model-helper/calls.json`, `flock`-protected, proved with ten racing processes |
| Wire protocol | Two operations, `ping` and `ask`. The caller cannot name a provider, model, binary or path |
| Eligibility | **Does not exist.** Nothing distinguishes an owner-initiated call from any other |

**The properties that must survive**, all established at real cost in Phases 07–09:

- `homelab-bot` cannot read either OAuth credential, and the credential never moves;
- the caller cannot name a program, path or binary — everything comes from a root-owned config;
- the model gets no tools, verified with a canary against a positive control;
- model output is never dispatched;
- caps are enforced **before** the call, so a refusal costs nothing.

## 3. Learning objectives

By the end the owner should be able to explain:

1. Why a caller declaring a *need* rather than a *model* is what makes models swappable, and what
   breaks if that direction is reversed.
2. Why eligibility belongs to the provider rather than to the model — a model has no terms of
   service; a subscription does.
3. Why an eligibility check that has only ever permitted is worthless, and how a fixture proves it.
4. What "models as configuration" does and does not buy: adding a *model* becomes config; adding a
   *provider* remains code, because a provider is an integration.

## 4. Functional objectives

1. **A model registry in configuration.** More than one model per provider, each an entry with its
   own properties.
2. ~~**A task-class → model policy**~~ **A routing-key → model policy** (ADR-034 §5), so the caller
   asks by *who it is* — a role — rather than by model name. Today the only caller is the bot; its
   key is fixed in root-owned config, not chosen per request (§6.5).
3. **An `unattended` field per provider**, enforced by refusal before the call.
4. **Separate caps for unattended work**, per ADR-026 §6 — either a lower cap or a floor reserved
   for owner-initiated calls.
5. **`/ask` behaves exactly as it does today** from Telegram. This phase is not a user-facing change.

## 5. Decisions already fixed

- **ADR-026** — this phase implements it and does not reopen it. Both subscription providers are
  `unattended: true` by the owner's decision of 2026-09-10, with the accepted risk recorded there.
- **ADR-025 §1, §8** — the credential boundary and the bounded outbound context are untouched. Only
  the question and the five `/status` figures leave the machine. **Widening that is not in scope.**
- **ADR-024** — the authorisation check stays in one function.
- **ADR-007** — model-agnostic. The registry is the mechanism, not an exception.
- **ADR-006** — the simplest thing that works. This phase must not acquire a gateway, a queue, a
  database or a dependency.
- **ADR-033** — Vercel AI Gateway is the metered provider; the spend governor ships with it or not
  at all. **Neither is built here.** The registry must leave room for a provider whose `unattended`
  is a policy choice and whose calls cost money — a `metered: true|false` field, unset today, is the
  whole accommodation. Anything more is designing 15.1 blind.
- **ADR-034 §5** — the router receives the role, a bounded task summary and validated metadata;
  priority/severity/complexity are hints, never selectors; routing starts deterministic and keeps
  deterministic as the fallback. This phase is the deterministic router and nothing more.
- **ADR-047 and `docs/standards/service-security-baseline.md`** — the helper stays `User=aleix` as
  a named exception; no new account, no new listener, no new group; secrets by `LoadCredential=`
  only (none are added here); the three measured limits in the standard are not re-tried.
- **Phase 13 handover items 1–5** are the operating envelope; item 2 (where a paid key lives) is
  15.1's, recorded here so the registry's provider entry has a field for it (`credential:` name,
  resolved by the unit, never a path the caller can supply).

## 6. Decisions still open

### 6.1 Where the routing-key → model mapping lives

Candidates: a table in `config.json`; a per-model list of task classes it can serve; or a policy
file. The registry must express "this model is cheap and good enough for classification" without
the caller knowing model names.

**Constraint:** the mapping is root-owned configuration, like everything else the helper reads. It
must not become something the caller can influence. **Recommendation (2026-09-13):** a `routes`
table in `config.json` keyed by routing key, each entry an ordered list of `provider/model` pairs;
the registry lists models under providers with `unattended` on the provider and `metered` (unset)
alongside. Unknown key → refused (§9). No policy file, no second format.

### 6.2 What happens when no eligible model exists

If an unattended request arrives and every provider that could serve its task class is
`unattended: false` or exhausted, the refusal must be **distinguishable** — "no eligible provider"
is a different fact from "all providers exhausted", and Phase 09 already learned that collapsing
distinct failures into one message costs an evening.

### 6.3 Whether `unattended` is declared per request or inferred

The bot is the only caller today and every call is owner-initiated. Options: default `false` and
require explicit opt-in; or carry a caller-supplied flag from the start.

**Recommendation to test in-phase:** default `false`, explicit opt-in. A field that must be set to
become dangerous is safer than one that must be set to become safe.

### 6.4 Whether fallback should cross routing keys

Today fallback walks the provider list in order. With task classes, "the cheap model is exhausted"
might reasonably fall back to a more capable one. That is a **cost** decision once providers are
metered, and it should probably be refused by default in this phase rather than designed blind.
**Recommendation:** refuse; fallback walks the route's own list only.

### 6.5 What routing key the bot sends, and how hints are carried — added 2026-09-13

The bot is the only caller and every call is owner-initiated. **Recommendation:** the bot sends no
key at all; the helper's root-owned config maps "no key" to a named default route
(`owner-interactive`) — the caller cannot influence the route, which keeps the Phase 09 property
(§9). The `ask` operation *accepts* the ADR-034 fields — `role`, `summary`, `priority`, `severity`,
`complexity` — validates their shape, logs them, and **uses only `role`** as the routing key. The
hints are carried so 23.0 does not have to change the wire protocol, and ignored so nothing can
select a model by asserting its task is hard. Test 11 proves the ignoring.

### 6.6 Whether the unattended budget is a cap or a floor (ADR-026 §6)

**Recommendation:** a floor reserved for owner-initiated calls — e.g. unattended may use at most
`per_day − reserve`. A floor is what protects `/status` and `/ask` for the owner when a scheduled
caller has burned the day; a lower cap alone does not. Decide with the numbers in the handover.

## 7. Implementation scope

1. Extend `config.json` into a registry: providers with eligibility, and models beneath them.
2. Extend the wire protocol's `ask` with the ADR-034 fields (`role` as the routing key; `summary`,
   `priority`, `severity`, `complexity` accepted, validated and logged, never selecting) and an
   `unattended` flag, all optional with safe defaults so an old caller keeps working.
3. Add the eligibility check in the helper, **before** the cap reservation, so an ineligible call
   costs nothing — the same ordering principle Phase 09 established for caps.
4. Extend `Limiter` with a separate unattended budget.
5. Update `install-model-helper.sh verify` to exercise the refusal, the unknown-key refusal, and
   the hints-do-not-select check.
6. Unit file: **no directive changes expected.** If one is needed, it goes through the standard
   (`# WHY`, score recorded before and after, none of the three measured limits re-tried).

### 7.1 Not in scope

Choosing a metered provider. Adding one. Any gateway. Observability beyond the existing journal
lines. Widening what leaves the machine. Conversation memory. Tool use. Anything in ADR-027.

## 8. Validation / tests

Every check reports `UNKNOWN` rather than a plausible-looking result when it cannot determine an
answer. **A check that has only ever permitted is unvalidated**, and this phase's central control is
a check that will permit every real call.

|---|---|---|
| 1 | Unattended request against a **fixture provider** set `unattended: false` | **Refused, on the reason** |
| 2 | Same request against a provider set `unattended: true` | Permitted — the positive control for test 1 |
| 3 | An ineligible request | Consumes **no** cap — assert the counter before and after |
| 4 | `/ask` from Telegram | Unchanged behaviour, live output captured |

| 6 | Old-style `ask` with no task class or flag | Still works |

| 8 | Caller attempts to name a binary, path or model | **Rejected** — the Phase 09 property must survive |
| 9 | `id homelab-bot` | Byte-identical |
| 10 | `sudo ss -tlnp` | ~~Still 6~~ **Still seven**, the same seven as the Phase 13 closing check |
| 11 | `ask` with `priority: critical`, `complexity: high` on the default route | Routed **exactly** as the same `ask` without them — journal line shows the hints logged and the same `provider/model` chosen |
| 12 | `ask` with an unknown `role` | **Refused**, on the reason, consumes no cap (assert counter) |
| 13 | `systemd-analyze security homelab-model-helper@.service` after install | **≤ 3.8**; every waiver still has its `# WHY` |

Test 1 without test 2 proves nothing: a refusal that happens because the fixture is broken looks
exactly like a refusal that happens because the check works.

**Fixture discipline, learned 2026-09-10:** a test fixture that does not match the real format
produces a confident negative indistinguishable from a finding. Assert the fixture's shape, not just
the outcome.

## 9. Security considerations

- **The caller must still be unable to name a program.** This phase adds fields to the wire
  protocol, which is exactly where that property could be lost by accident. A task class is a
  *lookup key into root-owned configuration*, never a value that reaches `argv`.
- **An unknown task class must be refused, not defaulted.** Defaulting to "the cheap model" would
  make a typo silently pick a model, and defaulting to the capable one makes a typo expensive.
- **The eligibility check is not a security boundary against the bot** — the bot is trusted to
  declare honestly. It is a control against *this project* building a scheduled caller later and
  forgetting what that implies. Recording that plainly matters, because a control mistaken for a
  stronger one is worse than none.
- **Caps are capacity protection, not billing.** That changes the moment a metered provider is
  added, and the code should not quietly assume flat-rate for ever.
- **No new listener, no new account, no new group.** If any of those appear, something is wrong.
- **Hints are data.** `priority`, `severity`, `complexity` are accepted so the protocol is stable
  for 23.0, and must be provably incapable of selecting a model or bypassing a cap (test 11). A
  reviewer reading the router must be able to find the one place the route is chosen and see that
  only the key reaches it.
- **The provider entry gains a `credential:` field for 15.1** (a name resolved by the unit via
  `LoadCredential=`, never a path). It is unset for both subscription providers and the code must
  not read it here — recording the shape is the accommodation, not implementing it.
- **The unit is the Phase 13 unit.** Any directive change is measured (test 13) and commented; the
  three measured limits in the standard are not re-tried.
