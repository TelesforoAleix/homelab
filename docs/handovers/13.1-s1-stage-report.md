## Findings for the orchestrator (each changes something the brief or ADR says)

1. **Two sudo parsers.** The node runs **sudo-rs 0.2.13** (`18-foundations-handover.md` package
   table; `backup-node.sh`'s pty comment). The MacBook's `visudo` is C sudo. Local proof therefore
   proves C-sudo syntax. The file uses only the subset both document (`Cmnd_Alias`, `NOPASSWD`, `!`,
   `*`); the installer runs the node's own `visudo -c -f` on the staged file **before** `install`,
   and removes the file if the installed copy fails a second check. No Docker on this MacBook, so no
   container check of sudo-rs was possible; the runbook says a rejection at that step is a stop, not
   a fix-on-the-node. **Residual: if sudo-rs matches arguments per-token rather than as one joined
   string, the glob-hole denies become no-ops — harmless, because the two-path allows then admit
   nothing extra either. The six probes in `verify` settle it on the node.**
2. **`install -m 600` (ADR §2, brief row 7) → `-m 644`.** Both installers write `config.json` as
   `root:root 0644` because the helper runs as `aleix` and the harness as `homelab-harness`. A
   `0600 root:root` config blinds both on their next start, and the agent has no `chmod`. The grant
   says `-m 644 -o root -g root`; `verify` asserts the file is still `root:root:644` after a
   re-install. **ADR-049 §2's table row needs the amendment at acceptance.**
3. **Row 11's `cp` → `cp -p`.** Root's `cp` without `-p` leaves the copy `root:root`, and `mv`-ing it
   back leaves `spend.json` unwritable by the helper — the ledger-restore defect the brief's §16
   says 15.1 S3 found. The allow is `cp -p …`; `verify` compares owner/mode before and after.
4. **Glob holes, closed by deny lines the ADR did not list.** sudoers matches arguments as one
   space-joined string and `*` matches a space, so every two-path allow admits a third argument
   (`cat a.json /etc/shadow b.json`), a later option (`cp -p x -t /tmp/homelab-agent y`;
   `install … x -t /etc/ssh/sshd_config.d y.json` — lockout-class), `..` traversal, and a second
   unit on `systemctl stop homelab-x ssh.socket`. `getent shadow` prints hashes. Added:
   `HOMELAB_AGENT_DENY_GLOB` (third argument, later option, `..`, for `cat`/`install`/`cp`/`mv`
   and the four mutating `systemctl` verbs) and `getent shadow*|gshadow*`; the credential globs
   cover `key`, `token`, `.cred`, `secret`, `credentials`, `shadow`, `/home/aleix/`, `/root/`.
   Consequence worth stating: a future config named like `*key*.json` would be denied to the agent.
5. **Deny after allow, not before.** sudoers is last-match-wins; ADR §2's "explicit `!` line before
   the allow" would lose wherever both match. The grant line lists the denies last; the file's
   header says why. Wording amendment for the ADR.
6. **Landing the sudoers file is itself lockout-class** by `safe-changes-headless.md` §1
   ("Authentication: `/etc/sudoers.d/`"): a parse error in any included file disables `sudo` for
   `aleix` too, and `sudo rm` then cannot undo it. The brief counts one lockout-class step (sshd);
   the runbook treats S2 as one window covering both, with **S2 holding a root shell (`sudo -i`)**
   opened before step 1 and the rollback typed there. Cheap, and it is what the standard says.
7. **Destructive deny probes.** Brief row 9 says attempt `reboot`, `usermod -aG sudo`,
   `data-volume.sh lock`. If a deny were broken, the attempt performs it. `verify` decides those
   three with `sudo -n -l <cmd>` (list mode, nothing runs) and attempts the harmless denies for
   real with stdout discarded (a broken `cat gateway-key` must not print the key into a log). If
   sudo-rs does not support `sudo -l <command>`, those three report UNKNOWN and stay with the
   owner's judgement — the runbook says not to "try it and see".
8. **Root pager.** `sudo systemctl status`/`journalctl` on a tty open `less` as root. systemd sets
   `LESSSECURE=1` when `SUDO_UID` is set; the alias adds `RequestTTY no` so the executor path has
   no pager. PREDICTED, with an owner check in the guide.
9. **§6.1, the password.** `useradd --password '*'` rather than `!`-locked: OpenSSH's own
   locked-account refusal keys on a leading `!` (bypassed under `UsePAM yes`, but `*` is
   unambiguous for both). `passwd -S` reports `L` either way; `verify` accepts `L` or `NP`.
