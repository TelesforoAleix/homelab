### The request schema, as it stands (23.1, 23.2, 23.3 — what it may extend)

`services/homelab-harness/README.md` §1–2 is the reference. Version `1`, closed field set. Fields a
successor may *add* are additive under `v: 1` only if absent-means-today; anything that changes a
meaning is `v: 2`. The eight identity names (`client`, `user`, `user_id`, `origin`, `peer`,
`identity`, `request_id`, `ts`) are reserved for the runtime forever.

### Unsatisfied controls

None against an accepted ADR. ADR-034 §13 (a model's tool request becoming an untrusted request) is
deliberately **not** taken — the canary re-ran through the endpoint and nothing was dispatched
(ADR-025 §10 stands). ADR-033 §5: no metered call was possible and none was made.

### Decisions that must not be silently inherited

- **`role` is required at the endpoint.** The helper defaults an absent role to `owner-interactive`;
  the endpoint refuses instead, so an agent's call never becomes the owner's without a decision.
  23.1's decomposition must keep that when it fans a request out.
- **Structural signals beat the declared `kind`.** A client can lift `unclassifiable` to `question`
  but cannot relabel work as a question. 23.1 replaces the refusal with decomposition; it must not
  soften the rule on the way.
- **The endpoint's state is on root and holds no content.** If a successor ever needs the endpoint to
  persist request content, that reopens the account question (ADR-047 trigger 3), not the state path.
- **The Telegram bot is not a client** (brief §6.7). What would change the answer: the endpoint
  offering something `/ask` cannot do directly (decomposition, context assembly), and a budget
  independent of the shared caps.
- **Roster name = role key.** Factory has no JSON agent manifests; `run` derives the agent from
  `assigned_agent`. When manifests exist, `run` reads the role from them, and the route table's keys
  follow.

### To Phase 23.1 — decomposition and service routing

- **The seam:** class `task` → `needs_decomposition`. **Work-shaped instructions are refused until
  decomposition exists** — rules T1–T4 in `classify.py`. Replace the refusal with a decomposition;
  keep the taxonomy revisable in guide + code (not an ADR).
- **Misclassified or unclassifiable requests seen in this phase:** none misclassified. `"the
  weather in Berlin tomorrow"` with no kind → `unclassifiable` (correct, by design). Known steerable
  edges in the README: a task phrased as a question is served as a question; "Write a haiku" is a task.
- **Capability gaps observed:** `Request.capabilities` reaches the endpoint and is used only to
  refuse (T2); the `homelab` adapter advertises none, so a capable agent is refused at activation.
- **The Telegram deferral** (§6.7) and what would change it, above.
- **Workbench facts for the client side:** roster name = role key; `run` sends empty `context`;
  `run` records a `run` object with existing statuses; the audit records absolute paths.

### To Phase 23.2 — context assembly

- `context` today: a list of `{text, source}` items the client **selected**; the endpoint renders
  them to the helper's single string (`[source: …]` prefix when given) and **adds nothing** — no
  logs, journals, config or files (ADR-039 §2). Provenance is carried as received. **Today Factory
  sends none**: `Request.context` is `tuple[str, ...]` (no source) and `run` sends `()` because
  nothing on a ticket is selected content. `context_items 0` on every real request.
- Where assembly sits: between `validate()` and `helper_payload()` in `harness.py`, producing the
  items the client did not — under ADR-039's selection rule, which is 23.2's to encode.
- The helper caps `context` at 2000 chars by truncation; the endpoint refuses at the same limit.

### To Phase 23.3 — governance

- **`client` is a label.** `X-Homelab-Client`, grammar `^[a-z0-9][a-z0-9-]{0,31}$`, recorded as
  `client_declared`. Identity attaches where the header is read (`Harness.handle_request_body`).
- **Correlation is audit machinery, and the interface will need one field for it.** The endpoint
  returns `request_id`; `Result` cannot carry it; the `homelab` adapter exposes it as
  `last_request_id` and `run` records it on the run object. That is a backend-specific concept
  reaching the Workbench through a side door instead of the interface — decided in 23.3, with the
  ADR-035 §4 amendment. Not added in 23.0 (`Request`/`Result` unchanged, so ADR-035 §4 stands as written).
- **The audit line schema** (`Audit.FIELDS`) and where approvals and budgets would attach: as
  fields on the line, closed-grammar or numeric, never text; `write()` refuses unknown keys.
- **The shared helper caps are the only budget today.**
- **What the ADR-034 §13 transition would change in the endpoint:** today a model's output is
  `text` and nothing else — the canary returned exactly `/restart ssh.service` and `NRestarts` stayed
  0. §13 would add a path from `text` to an untrusted request checked by the runtime; that path does
  not exist and must be built as a refusal-first structure, not bolted onto `handle_request_body`.

### To Phase 19 — tool vocabulary

- `Request.capabilities` was carried and used only to refuse. The `homelab` adapter's
  `capabilities()` and `tools()` return `()` — the honest statement that the endpoint executes
  nothing. A real capability check needs: manifests that declare capabilities (Factory has none as
  JSON), a backend that advertises concrete tools, and the ADR-034 §10 mapping between them.

## 3. What was implemented / final state

See the guide's *Implementation* and *Reference-build choice*. In one paragraph: a stdlib
`ThreadingHTTPServer` as `homelab-harness` on loopback; layer 1 validates a closed schema and refuses
identity claims by name; layer 2 classifies deterministically into four classes and refuses three;
layer 9 forwards a `question` over the 15.0 wire protocol with `role` as the only routing key,
returns the answer with a `request_id`, and writes a content-free audit line. ADR-048 gives the
helper's socket a consumers group. The `homelab` adapter and `run` make the Workbench the first
client; the §8.1.3 check proves the interface.
