## Outcome

**Complete.** ADR-038 is true on the machine: the five repositories are clones inside the encrypted
volume, the Factory Workbench runs on the node as a systemd service on loopback, the MacBook reaches
it only through an SSH tunnel, the unit is skipped — not failed, and without paging anyone — while
the volume is locked and starts on unlock, every listening socket is named, and the watchdog carries
no dependency on any of it. All sixteen rows of the brief's §8 were observed by the owner on the node
on 2026-09-12, including a locked reboot and a crash loop. No ADR was needed; §6's recommendations
were taken, two with amendments recorded below.

One row failed on its first run and the cause is the most useful thing this phase produced: see
*Problems*, item 1.

## Problems / failures / lessons

1. **`WorkingDirectory=` on the volume defeated the Condition and paged the owner about a locked
   volume.** *Assumption:* `WorkingDirectory=/srv/homelab/factory` is the obvious way to make `python3
   -m workbench.cli` resolve and is harmless. *What happened:* install, enable, start and the locked
   boot all passed. Row 3 — `lock`, then `systemctl start` — returned rc 1, `A dependency job for
   homelab-workbench.service failed`, journal `failed with result 'dependency'`, `Triggering
   OnFailure= dependencies`, and a Telegram alert (19:17 UTC). `systemctl show` had
   `RequiresMountsFor=/srv/homelab/factory` and `srv-homelab.mount` in `Requires=`. *Learned:*
   systemd derives an implicit `RequiresMountsFor=` from `WorkingDirectory=`; **dependency jobs run
   before conditions are evaluated**, so the mount job failed on the locked LUKS volume and
   `ConditionPathIsMountPoint=` was never consulted. A locked *boot* hides this entirely — nothing pulls
   the unit until the target starts — so ADR-038's validation 3 was being met by the wrong mechanism,
   and only the manual-start canary exposed it. *Changed:* `WorkingDirectory=` removed,
   `Environment=PYTHONPATH=/srv/homelab/factory` added (the Workbench writes nothing relative to cwd);
   the culprit bisected unprivileged with throwaway user units (`ReadWritePaths=`, `ProtectSystem=`,
   `Environment=`, `ExecStart=` add nothing); the standard gained a row and a post-edit check; row 3's
   Expect gained "no alert". Commit `55f17db`.
2. **The forward on `Host homelab` broke every scripted SSH.** `backup-node.sh` died at its first
   `ssh homelab` with `bind [127.0.0.1]:8765: Address already in use … Could not request local
   forwarding` because the owner's tunnel session held the port and `ExitOnForwardFailure` refused.
   The verifier the same; `scp`, VS Code Remote and git over SSH would have been next. Row 16 passed
   only after closing the tunnel. *Changed:* `Host homelab-workbench` carries the forward; `homelab`
   carries nothing (`a1e450e`). A forward belongs on the alias whose only job is the forward.
3. **The brief assumed the Workbench commits and pushes.** It does not — `gitops.py` is called only
   by the acceptance script. Found in S1 by reading `engine.py`; §6.6, §8 row 7 and §16 risk 1
   rewritten before implementation (`8045856`). The risk is not "push fails silently" but "nothing
   pushes".
4. **The workspace was not Workbench-initialised.** `serve` would have refused at start (`has no
   project.json`). Fixed in `factory-ops` by `workbench.cli init`, proved additive on a scratch copy
   first. The brief's "no change to any private repository is required" was false; found before, not
   after.
5. **A real action on a legacy record creates a duplicate, not an update.** `records.path_for()`
   writes `<ID>.yaml`; the legacy files are `<ID>-<slug>.yaml`. Row 7 produced
   `TICKET-2026-0023.yaml` beside `TICKET-2026-0023-interaction-schema.yaml`. Same family as the 93
   legacy-status validation problems. A `factory-ops` finding; the Workbench runs, real use waits.
6. **The kill loop tripped on kill 5, not 6.** `StartLimitBurst=5` counts *starts* in the window, and
   the unlock's start after row 11 was inside it. Predicted 6; observed 5; both correct. Written down
   so nobody "fixes" the unit.
7. **The password exposure** (Security notes). A silent multi-second `sudo` loop invites a retyped
   password. The verifier gets a progress line as a recorded issue.
8. **Two small traps.** `systemctl show -p A,B` prints in systemd's order, not yours — the first read
   of F5 looked wrong and was right. Python block-buffers stdout to the journal; `PYTHONUNBUFFERED=1`
   is in the unit for that reason.
9. **The executor's first negative test was not one.** "ls-remote without the key" still used the key
   through `~/.ssh/config`; replaced with the anonymous-HTTPS pair, which is a real refusal with a
   real control.
