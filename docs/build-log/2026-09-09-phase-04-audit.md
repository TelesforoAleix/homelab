# 2026-09-09 — Phase 04: the pre-publication audit

The gate. Nothing was pushed until this ran. Recorded here because a security control that leaves
no evidence is indistinguishable from one that never ran.

## What was scanned

**Objects reachable from all refs**, not the working tree. `.gitignore` is not retroactive: it stops
git tracking files it is not already tracking, and it never removes anything. A secret committed in
one commit and deleted in the next is still in the history, and `git clone` hands it to anyone.

Reachable-from-a-ref is also exactly the set `git push` transfers, so it is the right scope for a
pre-publication check.

```text
Objects reachable from all refs: 385
Of which file contents (blobs):  213
Binary blobs skipped:            0
Blobs actually searched:         213  (1310489 bytes)
```

A `git bundle` of the complete history was taken first and verified with `git bundle verify`
("The bundle records a complete history", 303 KB), so that nothing done during the audit could be
unrecoverable.

## Problem 1 — the scan reported everything clean because it searched nothing

The first run of `scripts/macos/scan-history.sh` looked like a pass:

```text
Binary blobs skipped:            213
  private keys                       clean
  SSH public keys                    clean
  ... all 16 classes clean ...
 VERDICT: no critical findings and nothing flagged for review.
```

**213 blobs, 213 skipped.** Every blob was classified binary, the corpus was empty, and all sixteen
pattern classes reported clean because there was nothing to search. The verdict was not wrong about
its inputs; it had no inputs.

**Cause.** The binary check was:

```bash
git cat-file -p "$hash" | head -c 8192 | LC_ALL=C grep -qU $'\x00'
```

A NUL byte cannot survive being passed to `grep` as a pattern. Arguments are C strings, so the NUL
terminates the string and the pattern arrives **empty**. An empty pattern matches every line, so
every blob was declared binary. The test did not fail — it inverted, silently, into "skip
everything".

**Fix.** Detect NULs by deleting them and comparing lengths, which never puts a NUL in an argument:

```bash
raw="$(git cat-file -p "$hash" | head -c 8192 | wc -c)"
stripped="$(git cat-file -p "$hash" | head -c 8192 | LC_ALL=C tr -d '\000' | wc -c)"
[ "$raw" != "$stripped" ] && skip
```

**The lesson, which this project has now learned three times.**

| Phase | Check | How it failed |
|---|---|---|
| 03 | `sshd -T` | Reported the configuration file, not the running daemon |
| 02 | `who` | Reported zero sessions, exit 0, on a machine with six |
| **04** | **binary detection** | **Skipped all 213 blobs and reported clean** |

All three fail by returning *nothing* and looking like success. `scripts/README.md` already carried
the rule — "a check that cannot determine an answer must say **unknown**, never a plausible-looking
zero" — and this script was written *by someone who had just written that rule* and still shipped the
bug. Knowing the failure mode is not the same as being immune to it.

**What changed beyond the fix.** The script now refuses to produce a verdict at all unless it can
prove it searched something:

- it prints `Blobs actually searched` and the corpus byte count, so an empty corpus is visible;
- it exits 2 if the corpus is empty;
- it runs a **positive control** — a string known to be in every commit of this repository — and
  exits 2 if that does not match. A scanner that cannot find something you know is there is broken,
  and must say so rather than say "clean".

The first two are hindsight. The positive control is the one worth carrying to other checks: it tests
the *instrument*, not the subject.

## Problem 2 — two false positives, one self-inflicted

The fixed run reported **2 CRITICAL classes**. Both were false positives.

**`wifi passphrase / psk` — 3 matches.** All three were historical versions of
`config/netplan/50-wifi.example.yaml`, containing:

```yaml
password: "REDACTED_DO_NOT_COMMIT_THE_REAL_PASSPHRASE"
```

The allow-list carried `REDACTED` on the serial-number class but not on the password class. Fixed by
adding `REDACTED|DO_NOT_COMMIT`.

**`tailnet names` — 2 matches.** Both were in **this phase's own brief**, committed an hour earlier,
where `*.ts.net` appears as literal pattern text in a table describing the sizing scan. The scanner
found its own documentation.

Fixed by requiring at least one leading character (`+` rather than `*` on the hostname class): a real
tailnet always has a name in front of `.ts.net`, whereas prose discussing the pattern does not. This
tightens rather than weakens the check.

**Also fixed:** the finding display printed no evidence for the password class. `grep -n` prepends
`NNN:` to each line, which defeats a `^`-anchored regex when extracting the matched tokens. The
display now strips the line-number prefix first. A finding you cannot see the evidence for is
difficult to adjudicate, and the temptation is to wave it through.

## Problem 3 — gitleaks silently skips merge commits

The independent cross-check, `gitleaks` 8.30.1:

```text
34 commits scanned.
leaks found: 1
```

**34, not 38.** The arithmetic is exact:

| Count | Value |
|---|---|
| All commits | 38 |
| Merge commits | 4 |
| Non-merge commits | **34** |
| gitleaks scanned | **34** |

gitleaks scans commit **diffs**, and a merge commit has no diff of its own by default. In this
repository the four merge commits are the **phase boundaries** — `77476eb`, `5804da6`, `0e26859`,
`8e42570`. Nothing was actually missed, because a `--no-ff` merge of an already-scanned branch
introduces no new content. But the blind spot is real, and in a repository where someone resolved a
conflict *inside* a merge commit, the resolved content would exist only there.

`scan-history.sh` walks reachable blobs, so commit topology cannot hide anything from it. This is the
clearest argument for having written our own: not that it is better, but that it is **wrong in
different places**. Recorded in `.gitleaks.toml` so the next reader does not have to rediscover it.

**gitleaks' one finding was also a false positive:** the `generic-api-key` rule flagged the word
`RAG`, at entropy 3.55, in the sentence "orchestration, model access, RAG/knowledge systems,
automation". Allow-listed as one specific adjudicated string — never a blanket path or rule
exclusion — because a scanner that always reports the same known-false result trains its reader to
ignore it.

## Problem 4 — the private-key check was dead, and only a planted secret revealed it

The scanner had reported "private keys: clean" on every run. That was not a result. The check had
never executed.

**How it was found.** A scanner validated only against clean data is unvalidated: it has never been
observed to *find* anything. So a file of six obviously-fake secrets was committed into the scratch
clone and the scanner run against it. Five were caught. One was not:

```text
  private keys                       clean          <-- planted key NOT found
  Tailscale auth keys                1 MATCHES -- CRITICAL
  GitHub tokens                      1 MATCHES -- CRITICAL
  MAC addresses                      1 MATCHES -- CRITICAL
  email addresses                    1 MATCHES -- CRITICAL
  tailnet names                      1 MATCHES -- CRITICAL
```

**Cause.** A PEM header begins with dashes, so the pattern is `-----BEGIN [A-Z ]*PRIVATE KEY-----`.
It was passed as `grep -n -E "$regex"`, and **grep parsed the pattern as command-line options**:

```console
$ grep -n -E "$pat" keytest.txt
grep: unrecognized option `-----BEGIN [A-Z ]*PRIVATE KEY-----'
$ echo $?
2
```

Two mistakes compounded, and the second is the serious one:

1. The pattern needed `-e` to mark it as a pattern rather than options.
2. `2>/dev/null` discarded the error message, and the code treated **grep exit 2 (error)** exactly
   like **grep exit 1 (no match)**. A check that could not run reported that it had run and found
   nothing.

So the single most important class in the file — the one that catches an actual SSH private key —
was silently non-functional. It would have stayed that way until the day it mattered, and on that
day it would have said "clean".

**Fix.** `-e` on every pattern and allow-list; and the exit status is now inspected, with anything
above 1 aborting the whole scan rather than being folded into a verdict:

```bash
hits="$(LC_ALL=C grep -n -E -e "$regex" "$WORK/corpus.txt")"
status=$?
if [ "$status" -gt 1 ]; then
  # A broken check is not a clean result. Refuse to report a verdict.
  exit 2
fi
```

**Re-run after the fix — all six planted secrets caught, exit 1:**

```text
  private keys        1 MATCHES -- CRITICAL   -----BEGIN OPENSSH PRIVATE KEY-----
  Tailscale auth keys 1 MATCHES -- CRITICAL   tskey-auth-kQ1bF7hZ2xNotARealKeyAtAll
  GitHub tokens       1 MATCHES -- CRITICAL   ghp_0000000000000000000000000000000000
  MAC addresses       1 MATCHES -- CRITICAL   a4:5e:60:c3:91:7f
  email addresses     1 MATCHES -- CRITICAL   someone.real@gmail.com
  tailnet names       1 MATCHES -- CRITICAL   homelab.pretend-tailnet-name.ts.net
 VERDICT: 6 critical class(es) matched. DO NOT PUBLISH.
```

**The real repository was then re-audited with the working scanner.** The verdict was unchanged — no
critical findings — so the publication decision stands. But the earlier evidence for it did not: a
"clean" from a check that never ran is worth nothing, and the repository had already been pushed by
the time this was discovered. The result was right; the proof was not. Those are different things,
and the honest record is that this was caught *after* publication rather than before.

**This is the fourth instance of the same failure family in three phases**, and the most severe:

| Phase | Check | Failure |
|---|---|---|
| 03 | `sshd -T` | Read the file, not the running daemon |
| 02 | `who` | Zero sessions, exit 0, on a machine with six |
| 04 | binary detection | Skipped all 213 blobs, reported clean |
| **04** | **private-key pattern** | **Could not run at all, reported clean** |

The first three return *nothing* and look like success. The fourth returns *an error* and looks like
success, which is worse, because an error was available to be noticed and was actively suppressed.

**The transferable lesson: test the detector against a positive case.** Every check in this project
so far has been validated by watching it agree with a healthy system. That only ever proves it can
say "fine". A check must also be shown to say "not fine" when the thing it looks for is actually
present — and the cheapest way to do that is to plant one on purpose, somewhere disposable.

## Adjudications — the borderline categories

Four classes needed human judgement. Publishing without deciding these would have meant publishing
without having considered them, which is the failure the brief was trying to prevent.

### Private (RFC 1918) addresses — 38 hits — **PUBLISH**

`192.168.1.57` (the node, 37 hits) and `192.168.1.112` (the MacBook, 2 hits).

Not routable from the internet. `192.168.1.0/24` is the most common home subnet in existence and the
specific host octet tells an attacker nothing they could not obtain by scanning a network they were
already on. Removing them would degrade the build logs, which show real command output, for no
security gain.

### Tailscale (CGNAT) addresses — 19 hits — **PUBLISH**

`100.71.62.71` (the node) and `100.69.244.33` (the MacBook).

Addresses in `100.64.0.0/10` are reachable only from inside the tailnet, and tailnet membership is
authenticated by device key. Knowing the address grants nothing without a key.

**The distinction that matters:** the tailnet *address* is not sensitive, but the tailnet *name* is —
it is an identifier tied to the owner's account, appears next to every node in `tailscale status`,
and is the thing Phase 03 had to tighten after it leaked into repo-bound output. The name remains
redacted throughout, as `<tailnet>` or `CHANGE-ME`, and `verify-remote-access.sh` still strips it.
Address published, name withheld, deliberately.

### Absolute home paths — 5 hits — **PUBLISH**

`/home/aleix/` (server) and `/Users/home/` (MacBook).

The admin username `aleix` is unavoidable in a guide that shows real output, and the repository is
published under the owner's real name as the git author regardless.

**This one is conditional, and the condition should be stated rather than assumed.** A known admin
username is harmless *because SSH accepts no passwords* (ADR-018: `publickey` only, no
keyboard-interactive, `PermitRootLogin no`). It is half of a credential pair whose other half cannot
be guessed or brute-forced. If password authentication were ever re-enabled, this adjudication
becomes wrong — the sensitivity of a fact depends on the controls around it, not on the fact.

### Long high-entropy strings — 5 hits — **PUBLISH**

Four are the Ubuntu ISO SHA256 from ADR-014 and `download-ubuntu-iso.sh`; one is an `scp`
verification hash in the Phase 02 build log. Checksums exist to be published — that is the entire
point of one. Expected false positives, kept as a class because the catch-all is there to make a
human look, not to be right.

## Result

| Scanner | Version | Scope | Real findings |
|---|---|---|---|
| `scan-history.sh` (first run) | this repo | 213 blobs | void — searched nothing (Problem 1) |
| `scan-history.sh` (second run) | this repo | 220 blobs, all refs | 0 critical, but the private-key class was dead (Problem 4) |
| `scan-history.sh` (validated) | this repo | 220 blobs, all refs | **0 critical**, 4 review classes, all adjudicated |
| `scan-history.sh` vs planted secrets | scratch clone | 6 planted | **6/6 caught**, exit 1 |
| `gitleaks` | 8.30.1 | 34 commits (diffs) | **0** after one prose false positive allow-listed |

**No secrets were found in the history, and none had to be removed.** The `.ts.net` sizing pass from
the brief held up: the only tailnet strings in 38 commits are the three placeholders. Phase 03's
tightening worked.

The two scanners disagreed in both directions — gitleaks found something ours did not (prose), ours
found four classes gitleaks did not (addresses, paths, checksums), and gitleaks skipped a class of
commits ours cannot skip. Agreement between two tools built on different assumptions is worth more
than confidence from either alone, and the disagreements were more informative than the agreement.

## Lessons

1. **A check that searched nothing reports clean.** Third occurrence in three phases. Instrument the
   instrument: print what was examined, refuse to report on an empty set, and run a positive control.
2. **Knowing a failure mode does not confer immunity to it.** The rule was already written down, by
   the same hand, one phase earlier.
3. **A scanner will find its own documentation.** Any repository that describes its own secret
   patterns will match them. Tighten the pattern rather than blanket-excluding the file.
4. **Two scanners are worth more than one**, specifically because they are wrong in different places.
5. **A detector that has only ever reported "clean" is unvalidated.** Plant a positive case
   somewhere disposable and confirm it fires. This is the lesson with the widest application beyond
   git, and it is how Problem 4 was found at all.
6. **Never let an error become a verdict.** `grep` exit 2 is not exit 1. Suppressing stderr on a
   security check bought nothing and hid a dead pattern.
7. **Adjudicate borderline findings in writing.** "Nobody objected" is not a decision, and the
   reasoning is what a future phase needs when the conditions change — as the `aleix` adjudication
   shows, since it is only correct while ADR-018 holds.
