### The modules, as the firmware reports them (`dmidecode -t 16,17`, 19:49)

```text
Physical Memory Array: Maximum Capacity: 32 GB, Number Of Devices: 2, Error Correction Type: None

ChannelA-DIMM0 (BANK 0): 16 GB SODIMM DDR4, Kingston, Part Number 99U5663-007.A00G,
                         Serial 11161410, Rank 2, Speed 2133 MT/s, Configured 2133 MT/s, 1.2 V
ChannelB-DIMM0 (BANK 2): 16 GB SODIMM DDR4, Kingston, Part Number 99U5663-007.A00G,
                         Serial 10107215, Rank 2, Speed 2133 MT/s, Configured 2133 MT/s, 1.2 V
```

`99U5663-007.A00G` is Kingston's internal code for `KVR26S19D8/16`. Both channels populated with
identical dual-rank modules on a Skylake controller is symmetric dual-channel; `dmidecode` has no
channel-mode field, so the locators are the evidence. The firmware reports `Speed: 2133` (the
running speed) rather than the SPD's 2666 — a reporting choice of this 2016 BIOS, not a fault.

## Problems / failed approaches

### 1. The cover would not close

After reassembly the cover stopped **4 mm short** of sliding home, and sat higher on the left (seen
from the front) than the right. The SSD bracket was checked and was not the obstruction. The cover on
this chassis is a slide-and-hook design: it has to be set down *forward* of its closed position with
every side hook in its slot and the rear lip *under* the rear panel's edge, then slid backward. Set
down too close to the rear, or slightly tilted, the rear lip lands *on* the panel and jams a few
millimetres short — which is what this looked like. Re-seating it further forward and sliding it
back closed it. No force was used. Lesson: the HMM's "slide to the front a small amount, then lift"
for removal reverses exactly, and "a small amount" is more than it feels like.

### 2. The stability test took the node off the network

`memtester 24G 1` was started over SSH. Within 15 s `systemd-networkd` logged
`wlp1s0: DHCP lease lost` and the node had no IP address for ten minutes; the owner's SSH session
died and both routes (tailnet, LAN) timed out from the MacBook.

**What it was not:** not a reboot (`uptime` continued), not a memory fault (no MCE, no EDAC line,
every memtester test up to that point `ok`), not a Wi-Fi drop (the association held; `[UFW BLOCK]`
lines from LAN neighbours kept arriving on `wlp1s0`), not OOM (no kill; swap stayed at 0 B).

**What it was:** the shared building network's DHCP server issues **3-minute leases**
(`LIFETIME=3min`, `T1=1min 30s`, from `/run/systemd/netif/leases/3`). With 24 of 30 GiB locked and
memtester saturating the memory bus, the renewal did not complete inside the window; `networkd`
treats an expired lease as an address to remove, and did. A lease was briefly re-acquired at
19:54:20 and lost again at exactly +3 min, and the address came back 19 s after memtester was killed.
The exact reason the renewal failed under load (driver receive buffers, or the client being starved)
was not pinned down; the correlation is unambiguous.

**What changed:** the test was re-run **from the console**, so a lost lease costs nothing, at 20 GiB
to leave more headroom. Two facts carried into the handover: a memory-stress test on this node is a
network outage and must be run from the console; and a 3-minute lease means *any* stall of a few
minutes drops the node's address — a property of the network, not of this phase, and worth Phase
14's attention (a static lease or a longer one is the gateway's decision, and the gateway is not
ours — ADR-016 / the 2026-09-10 reassessment).

### 3. The console was not attached for the first boot

The plan said attach it; the owner powered on headless, and it worked because POST had nothing to
say about a memory *increase*. Recorded as a deviation, not a failure — and the console was needed
twenty minutes later for problem 2, which is the actual argument for keeping it in the drawer next
to the machine rather than for attaching it pre-emptively.

## What we learned

- A memory change on this platform is invisible to POST unless memory *decreases*. Boot proceeded
  unattended; the BIOS password, Secure Boot and the boot-order lock were not involved.
- The first POST with new modules is slow — 17 s against 5.7 s — and it is one-off training, not a
  fault. Whether it stays at 17 s is for the next boot to show; the number is recorded so that a
  reader can compare.
- **A stress test can be an outage.** On a node whose only link is Wi-Fi on a network with 3-minute
  DHCP leases, anything that stalls the renewal for three minutes drops the address. `memtester`
  did it twice, reproducibly. Run such tests from the console; and Phase 14 should know the lease
  length when it thinks about what "reachable" means.
- The cover is a slide-and-hook lid. "Slide to the front a small amount" on removal means further
  than it feels like on reassembly.
- `dmidecode` reports slots, not channel mode. The locators are the dual-channel evidence.
- The `poweroff` path, unobserved since Phase 12, classifies as `clean reboot` — PID 1's
  `Shutting down.` is written on a power-off too. Correct, and now proved rather than assumed.
