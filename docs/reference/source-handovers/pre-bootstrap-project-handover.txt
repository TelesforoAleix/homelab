## Home Lab — Project Handover

### Project purpose

The **Home Lab** is a learning-first infrastructure project for experimenting with AI systems, agents, orchestration, model access, RAG/knowledge systems, automation, and eventually local models.

The objective is **not simply to install an existing AI agent**. The goal is to understand the different layers of an AI system by building and evolving them deliberately.

Long term, the Home Lab should become a small, self-hosted AI platform where different interfaces can send requests into the system, different AI models/agents can process them, and different tools/services can execute work.

It should also become a **public portfolio project** with a repository that documents the architecture, decisions, setup, code, experiments, and enough instructions for someone else to reproduce it.

---

# 1. Hardware

Selected machine:

**Lenovo ThinkCentre M700 Tiny**

Current known configuration:

* Intel **Core i5-6600T**
* 4 cores / 4 threads
* **8GB DDR4**
* **256GB SSD**
* built-in **Wi-Fi**
* Bluetooth
* Tiny form factor
* purchased for **700 DKK**

The machine is deliberately inexpensive because the first version is primarily an **orchestration/server machine**, not an AI inference workstation.

The existing Windows installation is temporary.

### RAM

The M700 has two SO-DIMM slots and supports up to **32GB DDR4**.

The current 8GB configuration is not yet known to be:

* 1×8GB, or
* 2×4GB.

This should be checked in Windows Task Manager before wiping Windows.

If it is **1×8GB**, likely upgrade paths are:

```text
8 + 8 = 16GB
```

or, if a cheap used 16GB SO-DIMM appears:

```text
8 + 16 = 24GB
```

32GB is not currently necessary.

There is an active plan to look for inexpensive used DDR4 SO-DIMM RAM on DBA, prioritizing good-value 16GB sticks rather than overpaying.

### Future hardware philosophy

Do not over-upgrade this machine.

Its role is:

> orchestration + infrastructure + agents + storage/services

not:

> local LLM inference.

If CUDA/local models become a major part of the project, the preferred architecture is eventually to add a **second GPU node**, rather than trying to turn the M700 Tiny into a GPU workstation.

Possible future architecture:

```text
M700
AI orchestration / control node
        │
        ├── cloud models
        ├── services
        ├── storage
        └── future CUDA GPU node
```

# 2. Operating system

Preferred OS:

**Ubuntu Server LTS**

Not Ubuntu Desktop.

The M700 should eventually operate completely **headless**.

Initial installation process:

1. Boot existing Windows.
2. Verify hardware:

   * CPU
   * RAM
   * RAM slots used
   * SSD
   * Wi-Fi
   * Bluetooth
   * USB
   * DisplayPort
   * fan/noise
3. Create Ubuntu Server installation USB from MacBook.
4. Completely wipe the existing Windows installation.
5. Install Ubuntu Server.
6. Enable OpenSSH during installation.
7. Once remote access works, disconnect the monitor/keyboard.

Windows has little value for this project.

# 3. Development workflow

The M700 is the **execution environment**, not the primary computer used for editing code.

The MacBook Pro remains the main development interface.

Preferred architecture:

```text
MacBook Pro
    │
    │ VS Code Remote SSH / Terminal
    ▼
M700
Ubuntu Server
    │
    ├── source code
    ├── Git
    ├── Docker
    ├── agents
    ├── databases
    └── services
```

The code can physically live on the M700 while being edited comfortably from the MacBook.

Primary remote-access tools:

* SSH
* SSH keys
* **Tailscale**
* VS Code Remote SSH

Tailscale should make the M700 securely accessible from outside the home network without directly exposing SSH to the public internet.

# 6. AI model access

The system should remain **model-agnostic**.

Initial models/tools:

### Claude

Use **Claude Code CLI**.

Authentication should initially use the existing Claude subscription rather than API billing where supported by the official CLI.

### OpenAI

Use **Codex CLI**.

Authentication should initially use the existing ChatGPT subscription where supported by the official CLI.

Therefore the first version does **not need API credits simply to experiment with Claude Code and Codex**.

Conceptually:

```text
Router
├── Claude Code CLI
├── Codex CLI
└── future executors
```

Later, proper APIs should intentionally be introduced as another learning stage.

This allows comparison between:

* subscription-backed CLI tools;
* direct API integrations;
* local models;
* hosted third-party models;
* model gateways.

The architecture should avoid hard-coding the entire system around one provider.

# 7. Telegram interface

Telegram is currently the preferred first remote interface.

A dedicated telephone number is **not required**.

Use a **Telegram Bot**.

Initial architecture:

```text
Telegram
   │
   ▼
Telegram Bot
   │
   ▼
Router
   │
   ├── Claude executor
   ├── Codex executor
   ├── shell/tools
   ├── knowledge search
   └── other services
```

The first implementation should be deliberately simple.

Possible early commands:

```text
/status
/uptime
/disk
/docker
```

Then progress toward:

```text
/claude ...
/codex ...
```

Eventually natural-language routing can replace explicit commands.

Example future request:

> Check why the API container is crashing, fix it and explain what happened.

The router should determine which executor/tool should handle it.

# 9. Agent architecture

There has been an important design decision:

**Do not begin by installing a giant autonomous agent framework and hiding all the infrastructure underneath it.**

Because this is a learning project, first build a simple version of the essential layers:

```text
interface
    ↓
router
    ↓
executor
    ↓
tool/system
```

For example:

```text
Telegram
↓
Python router
↓
Claude CLI
↓
output
↓
Telegram
```

Once this works, introduce an existing agent framework and compare:

> What does the framework replace?

> What abstractions does it provide?

> What problems does it solve?

> What complexity does it introduce?

This should provide much stronger understanding than starting with a black-box agent framework.

The long-term system is better understood as an **agent platform** rather than one single agent.

# 10. Knowledge system / “second brain”

A later component should provide agents with access to personal/project knowledge.

Potential sources:

* PDFs
* notes
* code
* documents
* project files
* datasets
* other user-owned information.

Conceptual architecture:

```text
Files
  │
  ▼
Indexer
  │
  ▼
Knowledge layer
  │
  ▼
Agent retrieval
```

Initially this will likely resemble a RAG architecture.

Later experiments can include:

* different embedding models;
* vector databases;
* hybrid search;
* reranking;
* metadata filters;
* graph-based retrieval;
* KAG/GraphRAG-style systems;
* alternative memory architectures.

The important design principle is:

> **storage and intelligence should be separated.**

Agents query knowledge; they do not own the underlying files.

# 12. Security model

The project will eventually give AI systems significant execution capability, so security is part of the learning project rather than something to bolt on at the end.

Important principle:

**Do not make the Telegram bot itself root.**

Prefer separation such as:

```text
Telegram
   │
bot service
   │
router
   │
controlled executor
   │
privileged operations
```

Potentially destructive actions should initially require explicit confirmation:

* `sudo`
* deleting files;
* removing packages;
* shutdown/reboot;
* firewall changes;
* Docker pruning;
* destructive database actions.

Other areas to learn:

* Linux permissions;
* service users;
* SSH keys;
* environment variables;
* secret management;
* API key management;
* logging;
* audit trails;
* container isolation;
* network segmentation;
* backups.

The server should eventually be treated as replaceable infrastructure.

# 14. Development philosophy

The project should optimize for **learning rather than fastest possible implementation**.

The objective is not:

> Get a personal AI assistant running as quickly as possible.

It is:

> Understand how modern AI systems are assembled, where the abstractions are, and how the components interact.

Therefore:

* use AI heavily to help write/build the system;
* but understand what the AI is creating;
* introduce abstractions progressively;
* build simple implementations before sophisticated frameworks;
* document architectural decisions;
* intentionally replace components to understand trade-offs;
* experiment rather than prematurely optimize for production.
